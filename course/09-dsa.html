9. Data Structures and Algorithms Basics

Choosing how to store data and how to process it efficiently.

📚 Start here: the messy bookshelf

A story Your friend has 10,000 books in a pile. "Find Dune," you say. They dig through the pile, one book at a time. That takes ages.

Now another friend has the books sorted alphabetically. To find Dune they open the middle: "M... too far, D is earlier." Open the middle of the first half: "G... too far." In about 14 steps they find it among 10,000 books.

Same books. Same goal. Different organisation. That's what data structures and algorithms are about: how you arrange data and what steps you follow.

Big-O: how does the work grow when the data grows?

Don't time your code in seconds; ask "if I have 10× more data, how much slower?"

Two searches, side by side

# Pile method: check each one. O(n)
def find(books, target):
    for i, b in enumerate(books):
        if b == target:
            return i
    return -1

# Sorted-shelf method: halve each time. O(log n). Needs SORTED data!
def bsearch(books, target):
    lo, hi = 0, len(books) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if books[mid] == target: return mid
        if books[mid] < target: lo = mid + 1     # throw away left half
        else:                   hi = mid - 1     # throw away right half
    return -1
Brain powerYou must check whether 100,000 incoming usernames already exist among 100,000 stored ones. With two nested loops that's 10 billion comparisons. What single change makes it ~100,000? Put the stored usernames in a set (or dict); each membership check becomes O(1).

The classic speed-up

# SLOW: for each name, scan the whole list → O(n²)
for name in new_names:
    if name in old_list:        # list scan!
        print("taken", name)

# FAST: build a set once → O(n)
old_set = set(old_list)
for name in new_names:
    if name in old_set:         # instant lookup
        print("taken", name)

There are no Dumb Questions

Q: How does a dictionary find things so quickly?

A hash function turns the key ("ana") into a number that points directly to a storage slot. No searching, just jump there. (Like a coat-check: your ticket number tells them exactly which hook.)

Q: Should I always optimise?

No. For 20 items, any approach is instant. Write clear code first, measure, optimise the part that is actually slow.

Q: Do I need to memorise sorting algorithms?

Not to write apps; just use the language's built-in sort() (it's O(n log n)). Do understand why some approaches get dramatically slower with more data.

Key points
  • The same data, organised differently, can be thousands of times faster to use.
  • Know the toolbox: list, dict, set, stack, queue, tree, graph.
  • Big-O describes how work grows with data size: O(1) < O(log n) < O(n) < O(n²).
  • Dicts and sets give near-instant lookups; avoid nested loops over big lists.

Classic algorithms

# Linear search: O(n)
def find(xs, target):
    for i, x in enumerate(xs):
        if x == target: return i
    return -1

# Binary search on a SORTED list: O(log n)
def bsearch(xs, t):
    lo, hi = 0, len(xs) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if xs[mid] == t: return mid
        if xs[mid] < t: lo = mid + 1
        else: hi = mid - 1
    return -1
  • Sorting: use the built-in; know that good sorts are O(n log n).
  • Duplicates? Putting items in a set turns an O(n²) comparison into O(n).
  • Space-time trade-off: caching/memoising uses memory to save time.
