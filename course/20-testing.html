20. Testing and Test-Driven Development

Code that checks your code, so you can change things without fear.

🧪 Start here: the smoke detector

A story You wouldn't build a house and then manually sniff for smoke every night. You install smoke detectors that watch 24/7 and shout when something's wrong.

Automated tests are smoke detectors for your code. Small programs that run your code with known inputs and shout if the answer is wrong. Change something at 2 a.m. and within seconds you know whether you broke anything, instead of finding out from an angry customer.

Your first test (the whole idea in 8 lines)

# discount.py
def price_after_discount(price, percent):
    return price - price * percent / 100

# test_discount.py        run with:  pytest
from discount import price_after_discount

def test_ten_percent_off():
    assert price_after_discount(200, 10) == 180

def test_zero_discount_changes_nothing():
    assert price_after_discount(50, 0) == 50

Each test follows Arrange → Act → Assert: set up the inputs, call the code, check the result. If an assert is false, the test fails and tells you exactly which.

  $ pytest
  test_discount.py ..                        [100%]
  2 passed in 0.01s            ✅

  (someone edits the formula by mistake)
  test_discount.py F.
  assert 190.0 == 180          ❌  ← caught immediately, with the exact line

What to test: think like a mischievous user

The happy path is easy. Bugs hide at the edges:

  • Empty: [], "", None
  • Zero, negative, huge numbers
  • Exactly on the boundary (the 18th birthday: is 18 an adult?)
  • Duplicates, wrong types, missing fields
import pytest
def test_discount_over_100_is_rejected():
    with pytest.raises(ValueError):
        price_after_discount(100, 150)      # this test FAILS now; it shows the code has no check!

The test pyramid: lots of small, few big

            /\
           /E2E\         few: drive a real browser through signup→checkout (slow, brittle)
          /──────\
         /integr. \      some: several parts together, e.g. handler + real test database
        /──────────\
       /   UNIT     \    many: one function at a time (milliseconds)
      /──────────────\

Fakes: swap out the slow, risky parts

Your checkout code charges a real credit card. In a test you don't want that! Replace the payment service with a fake (a "stunt double"):

class FakePayments:
    def __init__(self): self.charged = []
    def charge(self, user, amount): self.charged.append((user, amount)); return True

def test_checkout_charges_the_total():
    pay = FakePayments()
    checkout(cart=[10, 20], user="ana", payments=pay)   # inject the fake
    assert pay.charged == [("ana", 30)]

Passing the dependency in as a parameter (dependency injection) is what makes this easy.

TDD: write the test first (Red → Green → Refactor)

  🔴 RED     write a tiny test for the next behaviour. Run it. It FAILS (as expected).
  🟢 GREEN   write the simplest code that makes it pass.
  🔵 REFACTOR clean up the code; tests protect you. Repeat.

Benefit: you think about what the code should do before how, and you always have a working safety net.

Brain powerYour project has "100% test coverage" yet a bug slips through. How? Coverage only measures which lines ran, not whether the tests checked the right things. A test with no assertions can give 100% coverage and catch nothing.

Good-test checklist

  • Fast and independent: order and time of day don't matter.
  • Clear names: test_expired_coupon_is_rejected.
  • One reason to fail.
  • Run automatically on every push (CI, module 25).
  • Flaky tests (sometimes pass, sometimes fail) destroy trust: fix or delete them.
  • Every bug fixed → add a test so it can't return.

There are no Dumb Questions

Q: Doesn't writing tests slow me down?

At first, a little. Soon it's much faster: no manual re-clicking, fearless refactoring, bugs caught in seconds instead of days.

Q: Do I need tests for everything?

Focus on important logic, tricky edge cases and anything that has broken before. Trivial one-liners can go without.

Q: What's the difference between a mock, stub and fake?

Rough guide: a stub returns canned answers, a mock also records/verifies how it was called, a fake is a simple working replacement (e.g. an in-memory database).

Key points
  • Tests are automatic smoke detectors for code; Arrange-Act-Assert.
  • Test the edges, not just the happy path.
  • Many unit tests, fewer integration tests, very few end-to-end tests.
  • Use fakes for slow/external things; TDD = red, green, refactor.
  • Coverage shows what ran, not what's verified. Add a test for every fixed bug.

📋 Quick reference: the details

Key ideaAn automated test runs your code with known inputs and checks the output. A good suite catches regressions in seconds instead of users catching them in production.

A unit test

# pricing.py
def total(prices, tax=0.1):
    return round(sum(prices) * (1 + tax), 2)

# test_pricing.py  (run: pytest)
from pricing import total

def test_total_adds_tax():
    assert total([10, 20]) == 33.0

def test_empty_cart_is_zero():
    assert total([]) == 0

def test_custom_tax():
    assert total([100], tax=0.2) == 120.0

Structure: Arrange (set up), Act (call), Assert (check). Name tests by behaviour. Test edge cases: empty, zero, negative, huge, None, duplicates, invalid input.

The test pyramid

LevelTestsSpeed / count
UnitOne function/class in isolationMilliseconds; many
IntegrationSeveral parts together (handler + real test DB)Slower; moderate
End-to-end (E2E)Whole app via a real browser (Playwright, Cypress)Slowest, flaky-prone; few, covering key journeys

Test doubles

Replace slow, unreliable or costly dependencies (payment API, email, clock) with mocks/stubs/fakes so tests are fast and deterministic. Don't over-mock: tests that only verify mocks prove nothing.

TDD: Red → Green → Refactor

  1. Red: write a failing test for the next small behaviour.
  2. Green: write the simplest code to pass.
  3. Refactor: clean up with tests as a safety net.

Benefits: forces clear requirements, testable design, instant feedback.

Good tests are

  • Fast, independent, repeatable, self-checking. Order and time of day must not matter.
  • Failing for one reason, with a message telling you what broke.
  • Coverage shows lines executed, not correctness. 100% coverage with weak assertions is false comfort.
  • Run automatically on every push (CI, module 25). Flaky tests (sometimes fail) should be fixed or removed quickly.
  • Every fixed bug gets a regression test (module 10).
