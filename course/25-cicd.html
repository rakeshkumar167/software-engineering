25. CI/CD: Automated Tests and Releases

Make shipping boring, frequent and safe.

🏭 Start here: the car factory assembly line

A story In an old-style workshop, one craftsman builds a whole car by hand, and when it's done, they hope it drives. A modern factory uses an assembly line: each stage does one job (weld, paint, test brakes), automatically, the same way every time. A defect is caught at the stage where it happens, not after the car is sold.

CI/CD is the assembly line for software. Every time someone pushes code, a robot runs the same checklist: build it, test it, scan it, and (if everything's green) ship it.

CI and CD, decoded

TermMeansPlain English
CI: Continuous IntegrationMerge small changes often; every change is built and tested automatically"Does it still work when combined with everyone else's code?"
CD: Continuous DeliveryEvery passing build is packaged and ready to release at a click"Always shippable."
CD: Continuous DeploymentEvery passing build goes to production automatically"Ship it. No human click."

Your first pipeline (GitHub Actions)

Create .github/workflows/ci.yml in your repo:

name: CI
on: [push, pull_request]            # run on every push and every PR
jobs:
  test:
    runs-on: ubuntu-latest          # a fresh, clean machine every time
    steps:
      - uses: actions/checkout@v4                 # get the code
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }
      - run: pip install -r requirements.txt      # install deps
      - run: pytest                               # run the tests (module 20)

Push it. Open the repo's Actions tab and watch ✅ or ❌ appear. That's it. You have CI.

The clean machine matters: it proves the project builds from scratch, not just on your laptop.

Protect the main branch

Turn on branch protection: a pull request can only merge if the pipeline is green and a teammate approved. Now "I forgot to run the tests" is impossible.

Why small and frequent beats big and rare

  Big release every 3 months:  500 changes → something broke → which one?? 😱
  Deploy 10× a day:              ~3 changes → broke → it's one of THESE 3. Roll back. 🙂
Brain powerYour pipeline takes 45 minutes, so nobody waits for it and people merge anyway. What could you do? Cache dependencies, run tests in parallel, run only affected tests, move slow end-to-end tests to nightly, use bigger runners. Aim for under ~10 minutes.

Habits of healthy pipelines

  • Build once, deploy that exact artifact everywhere (config injected per environment, module 23).
  • Red main = emergency: fix or revert immediately.
  • Secrets live in the CI's secret store; never print them in logs.
  • Database migrations: make changes compatible with the old and new app versions (add new column, deploy, later remove the old one), or a rollback breaks.
  • Feature flags: deploy code dark, enable it later.
  • Versioning: MAJOR.MINOR.PATCH (e.g. 2.4.1): major = breaking, minor = new feature, patch = bug fix.

There are no Dumb Questions

Q: Isn't deploying automatically dangerous?

Less than manual, big-bang deploys, provided you have good tests, small changes, health checks, canary releases and one-click rollback. Safety comes from the automation.

Q: GitHub Actions, GitLab CI, Jenkins: which?

Same idea: a config file in your repo describing steps. Use whichever matches where your code lives.

Q: What if tests are flaky?

Fix or quarantine them quickly. If people learn "just re-run it," a real failure will get ignored.

✏️ Sharpen your pencil: order the pipeline

Put in a sensible order: deploy to production, run unit tests, build container image, install dependencies, checkout code, deploy to staging.
Answer: checkout → install deps → run unit tests → build image → deploy to staging (smoke test) → deploy to production.

Key points
  • CI = every push is built and tested automatically; CD = passing builds are released automatically (or on approval).
  • A pipeline is a repeatable sequence in a config file stored with the code.
  • Small, frequent releases are safer and easier to roll back.
  • Keep it fast, keep main green, protect secrets, build once, use flags and compatible migrations.

📋 Quick reference: the details

Key ideaContinuous Integration (CI): every push is automatically built and tested. Continuous Delivery/Deployment (CD): passing builds are automatically packaged and released (delivery = one approval click; deployment = fully automatic).

The pipeline

push / pull request
   → checkout code
   → install dependencies (cached)
   → lint + type check
   → unit + integration tests
   → build artifact / Docker image
   → security scan
   → deploy to staging → smoke tests
   → (approval) → deploy to production → health check → (rollback if bad)

Example (GitHub Actions)

# .github/workflows/ci.yml
name: CI
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }
      - run: pip install -r requirements.txt
      - run: pytest

Others: GitLab CI, Jenkins, CircleCI. All run the same idea: a clean machine executes your steps from a config file stored in the repo.

Why it matters

  • Catches breakage minutes after the change, while it's fresh in memory.
  • Small, frequent releases are less risky than big infrequent ones and easy to roll back.
  • Same automated steps every time: no "forgot to run tests" or hand-typed deploy commands.
  • Branch protection: PR can't merge unless CI is green and a teammate approved.

Practices

  • Keep the pipeline fast (under ~10 minutes): cache dependencies, run tests in parallel. A broken pipeline is everyone's top priority.
  • Build once, deploy the same artifact to every environment, with config injected per environment (module 23).
  • Store pipeline secrets in the CI secret store; never print them in logs.
  • Feature flags decouple deploy from release. Database migrations must be backwards-compatible with the previous app version for safe rollouts.
  • Version releases (semantic versioning MAJOR.MINOR.PATCH) and keep a changelog; tag in git.
  • Track DORA metrics: deploy frequency, lead time, change failure rate, time to restore.
