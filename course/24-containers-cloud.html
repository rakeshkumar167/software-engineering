24. Containers (Docker), Deployment and Cloud Basics

Packaging an app so it runs the same everywhere, and putting it on someone else's computers.

📦 Start here: the shipping container

A story Before 1956, loading a ship meant handling barrels, sacks and crates of every shape: slow and chaotic. Then someone invented the standard shipping container. Any cargo goes inside; cranes, trucks and ships handle the box without caring what's in it.

Software had the same chaos: "It works on my laptop but not on the server, because the Python version differs!" A software container (Docker) packs your app and everything it needs into one standard box that runs identically on your laptop, a colleague's, and the cloud.
  Without containers                    With containers
  laptop:  Python 3.9, lib v1           ┌─ container ─────────┐   same box runs on:
  server:  Python 3.12, lib v2   💥      │ app + Python 3.12    │ ─► laptop ✅
  (different, so bugs appear)            │ + exact libraries    │ ─► CI server ✅
                                         └──────────────────────┘ ─► cloud ✅

Image vs container (module 1 echoes!)

Docker wordMeaningAnalogy
ImageRead-only template with your app + dependenciesA recipe / program on disk
ContainerA running instance of an image (an isolated process)A cook cooking / a running process
RegistryStore for images (Docker Hub, ECR)A cookbook library

Container vs VM: a VM carries a whole guest operating system (heavy, minutes to boot). A container shares the host's kernel and bundles only the app's libraries: megabytes, starts in a second.

Write a Dockerfile: the recipe for your box

# Dockerfile
FROM python:3.12-slim              # 1. start from an image that has Python
WORKDIR /app                       # 2. work inside /app
COPY requirements.txt .            # 3. copy ONLY the dependency list first
RUN pip install -r requirements.txt   #    install (this layer gets cached!)
COPY . .                           # 4. then copy your code
EXPOSE 8000                        # 5. documentation: app uses port 8000
CMD ["gunicorn", "-b", "0.0.0.0:8000", "app:app"]   # 6. how to start
$ docker build -t pet-shop:1.0 .                       # make the image
$ docker run -p 8080:8000 -e DATABASE_URL=... pet-shop:1.0
$ curl localhost:8080                                   # host port 8080 → container 8000
$ docker ps          # running containers
$ docker logs <id>   # what is it saying?
$ docker stop <id>
Brain powerWhy copy requirements.txt and install before copying the rest of the code? Docker caches each step. If only your code changed, the slow install step is reused from cache and the rebuild takes seconds.

Three gotchas every beginner hits

1️⃣ Can't reach the app? Inside a container 127.0.0.1 means "this container only". Listen on 0.0.0.0.
2️⃣ Data vanished? A container's filesystem is disposable. Use volumes or a separate database for anything permanent.
3️⃣ Secrets in the image? Anyone with the image can extract them. Pass secrets at runtime (-e / platform secrets).

Docker Compose: a whole stack with one command

# docker-compose.yml
services:
  web:
    build: .
    ports: ["8080:8000"]
    environment:
      DATABASE_URL: postgres://app:pw@db/shop
    depends_on: [db]
  db:
    image: postgres:16
    environment: { POSTGRES_PASSWORD: pw, POSTGRES_USER: app, POSTGRES_DB: shop }
    volumes: [dbdata:/var/lib/postgresql/data]
volumes: { dbdata: {} }
# run everything:   docker compose up

Deploying without scaring your users

  Rolling:     replace servers one by one
  Blue-green:  [BLUE: current] ◄─ users       build GREEN on the side, test it,
               [GREEN: new]                    then flip traffic ─► GREEN (flip back = instant rollback)
  Canary:      5% of users ► new version, 95% ► old.  Watch metrics. Then 25%… 100%.

There are no Dumb Questions

Q: Do I need Kubernetes?

Probably not at first. It runs and heals many containers across many machines, but it's complex. Start with one container on a managed platform.

Q: Is a container a security boundary?

A decent one, but weaker than a VM since the kernel is shared. Run as non-root, use trusted base images, keep them updated.

Q: "Serverless" has servers?

Of course; you just don't see or manage them.

✏️ Sharpen your pencil: debug the container

docker run -p 8080:8000 app starts fine, but curl localhost:8080 is refused. The app prints "Listening on 127.0.0.1:8000". Why?
Answer: it binds to the container's own loopback, so the port mapping can't reach it. Make it listen on 0.0.0.0:8000.

Key points
  • Container = app + dependencies in an isolated, portable box; image = template, container = running instance.
  • Dockerfile builds images; order steps for caching; containers are ephemeral (use volumes/databases).
  • Compose runs multi-service stacks locally.
  • Cloud: IaaS → PaaS → serverless → SaaS = less to manage. Watch costs.
  • Deploy safely: rolling, blue-green, canary, and always keep a rollback.

📋 Quick reference: the details

Key ideaA container packages your app with its dependencies and runs as an isolated process sharing the host's kernel. It is lighter than a virtual machine and answers "works on my machine".

Container vs VM

Virtual machineContainer
IncludesFull guest OS + appApp + libraries only
StartupMinutesSeconds or less
SizeGBsMBs
IsolationStrong (own kernel)Process-level (namespaces, cgroups)

Vocabulary: image = read-only template (like a program); container = running instance (like a process, module 1); registry = image store (Docker Hub, ECR).

Dockerfile and commands

# Dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt   # cached layer
COPY . .
EXPOSE 8000
CMD ["gunicorn", "-b", "0.0.0.0:8000", "app:app"]
docker build -t myapp:1.0 .
docker run -p 8080:8000 -e DATABASE_URL=... myapp:1.0   # host:container port
docker ps / docker logs <id> / docker stop <id>
  • Layers are cached; put rarely-changing steps first.
  • Container filesystem is ephemeral: data written inside is lost; use volumes or a database service.
  • Bind to 0.0.0.0 inside the container, not 127.0.0.1, or the port mapping can't reach it.
  • Docker Compose runs multi-container setups (app + database + cache) from one YAML file.
  • Don't bake secrets into images; pass them at runtime. Run as non-root. Use small trusted base images.

Orchestration

Kubernetes (and simpler managed options like ECS, Cloud Run) schedule containers across machines, restart failures, scale replicas and roll out updates gradually. Powerful but complex: use a managed platform until you need more.
