17. OAuth 2, OpenID Connect, JWT, Password Hashing and MFA

Module 5 in depth: how modern apps really log people in.

🔑 Start here: the hotel valet key

A story When you hand your car to a hotel valet you don't give them your master key. You give a valet key: it starts the engine and drives, but can't open the glovebox or trunk, and it's useless once you collect the car.

OAuth 2 is a valet key for your online accounts. Example: a photo-printing app wants to read your Google Photos. You don't give it your Google password. Instead Google hands the app a limited, temporary token: "may read photos, nothing else, for one hour."

The OAuth dance (authorization code flow)

  You          PrintApp                     Google
   │ "connect Google Photos"
   │ ──────────►│
   │            │ ── redirect to Google ───────►  1. "PrintApp wants: read photos"
   │ ◄──────────┴────────────────────────────────    Do you allow?  [Allow] [Deny]
   │ you log in AT GOOGLE and click Allow ──────►
   │ ◄── Google redirects back to PrintApp with a one-time CODE ──
   │            │ ── CODE + app secret ────────► 2. server-to-server swap
   │            │ ◄── ACCESS TOKEN (valid ~1h) ──
   │            │ ── GET /photos  Bearer token ► 3. API checks token & scope
   │            │ ◄── your photos ───────────────
  • Scope: exactly what's allowed ("photos.read"). Least privilege.
  • Access token: short-lived key to call the API. Refresh token: longer-lived, used to quietly get new access tokens.
  • PrintApp never saw your Google password. And you can revoke it later.

"Sign in with Google" is OpenID Connect (OIDC)

OAuth answers "what may this app access?" (authorization). OIDC adds "who is this person?": Google also returns an ID token saying "this is Ana, ana@gmail.com, verified." Your app trusts Google's word and creates its own session (module 5).

JWT: a tamper-evident note

A JSON Web Token has three parts joined by dots:

  eyJhbGciOi...  .  eyJzdWIiOiI0MiIsInJvbGUiOiJhZG1pbiJ9  .  SflKxwRJSMeKKF2Q...
  └ header ─────┘   └ payload (the claims) ─────────────┘     └ signature ──────┘
                      {"sub":"42","role":"admin","exp":1700000000}
Brain powerIs a JWT encrypted? No! The payload is just Base64 text; anyone can read it. The signature only proves nobody changed it. Never put secrets inside. And the server must verify the signature, expiry and audience; decoding alone proves nothing.

Passwords, done properly

  signup:  "hunter2" + random SALT "x9Qa..."  ──► [ Argon2 / bcrypt ] ──► $argon2id$...  (stored)
  login:   typed password + stored salt       ──► [ same hash ]        ──► compare with stored
  Plain password is NEVER stored. Salt makes identical passwords hash differently.
  • Hashing is one-way: you can't "decrypt" it.
  • Slow on purpose (bcrypt/Argon2) so attackers can't test billions of guesses per second.
  • Rate-limit login attempts; don't say which half (email or password) was wrong.

MFA and passkeys

  • MFA = two or more of: something you know (password), have (phone/security key), are (fingerprint). Stolen password alone is no longer enough.
  • TOTP authenticator apps > SMS (SIM-swapping risk).
  • Passkeys (WebAuthn): your device holds a private key; the site stores only the public key. Nothing to phish, because the key only works for the real domain. This is where logins are heading.

There are no Dumb Questions

Q: Why does the app exchange a "code" for a token instead of Google sending the token directly?

The code travels through the browser URL (visible to many things). The real token is fetched server-to-server, where only the app (with its secret) can get it.

Q: Is OAuth for login?

On its own, no: it's for delegated access. Login is OIDC built on top of it.

Q: Where should I store a JWT in a browser?

An HttpOnly; Secure; SameSite cookie is generally safer than localStorage, which any XSS-injected script can read.

✏️ Sharpen your pencil: what's wrong?

A developer stores passwords as sha256(password) with no salt. List two problems.
Answer: (1) SHA-256 is extremely fast, so attackers can test billions of guesses/second; use Argon2/bcrypt. (2) No salt: identical passwords share identical hashes, and precomputed "rainbow tables" crack them instantly.

Key points
  • OAuth 2 = delegated, scoped, revocable access without sharing passwords. OIDC adds identity.
  • JWT = signed (not encrypted) token; always verify signature, expiry, issuer, audience.
  • Store passwords as slow salted hashes (Argon2id/bcrypt).
  • Use MFA; passkeys are phishing-resistant.

📋 Quick reference: the details

Key ideaOAuth 2 lets an app get limited access to your data at another service without ever seeing your password. OpenID Connect (OIDC) adds a standard way to learn who you are.

OAuth 2 roles and flow (Authorization Code)

  • Resource owner: the user. Client: the app wanting access. Authorization server: issues tokens (Google, Okta). Resource server: the API holding data.
  1. App redirects user to the provider with client_id, requested scopes (e.g. email calendar.read), redirect_uri, a random state.
  2. User logs in at the provider and approves the scopes.
  3. Provider redirects back with a short-lived authorization code.
  4. App's server exchanges code + client secret for an access token (and refresh token). (Public clients add PKCE.)
  5. App calls the API with Authorization: Bearer <access_token>.
  • Access token: short-lived (minutes), grants access. Refresh token: long-lived, gets new access tokens; guard carefully.
  • OIDC adds an ID token (a JWT with the user's identity: sub, email) = "Sign in with Google".
  • The state parameter prevents CSRF on the callback.

JWT: JSON Web Token

eyJhbGciOiJIUzI1NiJ9 . eyJzdWIiOiI0MiIsImV4cCI6MTcwMDAwMDAwMH0 . SflKxwRJSMeKKF2QT4fw...
     header                       payload (claims)                      signature
  • Header and payload are just Base64-encoded JSON, readable by anyone. The signature proves they weren't altered (needs the secret/private key).
  • Claims: sub (subject), iss (issuer), aud (audience), exp (expiry).
  • Server must verify signature, exp, iss, aud, and a fixed allowed algorithm (reject alg: none).
  • Don't put secrets in a JWT. Hard to revoke before expiry, so keep short lifetimes.
  • Storing in localStorage exposes it to XSS; an HttpOnly cookie is often safer for browsers.

Passwords done right

  • Store hash(password + unique salt) using a slow, memory-hard algorithm: Argon2id, scrypt or bcrypt. Not MD5/SHA-1/plain SHA-256.
  • Salt: random per-user value; defeats rainbow tables and shows identical passwords as different hashes. Optional pepper: secret key stored outside the DB.
  • Compare with constant-time functions; rate-limit logins; avoid revealing whether the email exists.
  • Prefer length over complexity rules; check against breached-password lists.

MFA and passwordless

  • TOTP apps (6-digit codes changing every 30 s), push approvals, SMS (weakest: SIM swap), hardware keys.
  • Passkeys / WebAuthn: public-key crypto; device keeps a private key, server stores only the public key. Phishing-resistant because the key is bound to the real domain.
  • Always offer recovery carefully; it's often the weakest link.
