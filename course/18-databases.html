18. Databases: SQL, Indexes, Transactions, NoSQL

Where applications keep data that must outlive the process.

🗄️ Start here: the library's filing room

A story Your program's memory is a whiteboard: wipe it (stop the program) and everything is gone. For anything that must last (customers, orders, photos) you need a filing room with a strict librarian who:
📂 stores records neatly in labelled cabinets (tables),
🔎 finds anything quickly using an index card system (indexes),
🤝 lets many people use it at once without messing each other up (transactions),
🔒 and never loses a record, even if the power goes out (durability).

That librarian is a database: a separate program (PostgreSQL, MySQL, SQLite, ...) your app talks to.

Tables: think spreadsheets that follow rules

  users                                    orders
  ┌────┬───────┬───────────────┐           ┌────┬─────────┬───────┐
  │ id │ name  │ email         │           │ id │ user_id │ total │
  ├────┼───────┼───────────────┤           ├────┼─────────┼───────┤
  │  1 │ Ana   │ ana@x.com     │◄──────────│ 10 │    1    │ 25.00 │
  │  2 │ Ben   │ ben@x.com     │◄──────────│ 11 │    2    │ 12.50 │
  └────┴───────┴───────────────┘     ◄─────│ 12 │    1    │ 40.00 │
   id = PRIMARY KEY (unique label)         user_id = FOREIGN KEY (points to users.id)

Instead of copying Ana's name onto every order, orders just point to her id. Update her name once and every order is right. This is normalisation.

SQL: the language of questions

SQL reads almost like English. The four everyday verbs (CRUD):

INSERT INTO users (name, email) VALUES ('Cy', 'cy@x.com');       -- Create
SELECT name, email FROM users WHERE id = 1;                      -- Read
UPDATE users SET name = 'Ana B.' WHERE id = 1;                   -- Update
DELETE FROM users WHERE id = 2;                                  -- Delete  (⚠ always use WHERE!)

JOIN glues related tables back together:

SELECT users.name, SUM(orders.total) AS spent
FROM users
JOIN orders ON orders.user_id = users.id     -- match rows via the key
GROUP BY users.name
ORDER BY spent DESC;

--  name | spent
--  Ana  | 65.00
--  Ben  | 12.50
Classic disaster: DELETE FROM users; (no WHERE) deletes everyone. Write the WHERE first, or run it as a SELECT first to see what would match.

Indexes: the book's index

Without one, finding email = 'ana@x.com' in 10 million rows means reading all of them. With an index (a sorted lookup structure) it takes ~25 steps.

CREATE INDEX idx_users_email ON users (email);

Trade-off: indexes take space and slow down writes a little. Index the columns you search, join or sort by.

Transactions: all or nothing

Sending 100 from Ana to Ben is two steps. What if the power dies between them? A transaction groups steps so either both happen or neither does:

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE owner = 'Ana';
UPDATE accounts SET balance = balance + 100 WHERE owner = 'Ben';
COMMIT;        -- both saved. (ROLLBACK would cancel both.)

Remember ACID: Atomic (all-or-nothing), Consistent (rules always hold), Isolated (people don't see each other's half-done work), Durable (saved means saved).

The #1 security rule: never paste user input into SQL

# 😱 DANGEROUS (SQL injection)
name = request.args["name"]               # attacker sends:  x' OR '1'='1
cur.execute("SELECT * FROM users WHERE name = '" + name + "'")   # returns EVERY user!

# ✅ SAFE: placeholders keep data separate from code
cur.execute("SELECT * FROM users WHERE name = %s", (name,))

Try it in 2 minutes (SQLite, no install on most computers)

$ sqlite3 demo.db
sqlite> CREATE TABLE pets (id INTEGER PRIMARY KEY, name TEXT, species TEXT);
sqlite> INSERT INTO pets (name, species) VALUES ('Rex','dog'), ('Tom','cat');
sqlite> SELECT * FROM pets WHERE species = 'cat';
2|Tom|cat

SQL vs NoSQL in one breath

  • SQL (relational): structured tables, relationships, strong guarantees. Start here by default (PostgreSQL).
  • Document (MongoDB): flexible JSON-like records.
  • Key-value (Redis): lightning-fast lookups, caches, sessions.
  • Graph (Neo4j): relationship-heavy data (social networks).
Brain powerA page showing 20 orders makes 21 database queries: one for orders, then one per order to fetch its customer. What's this called and the fix? The "N+1 query problem". Fix with one JOIN, or eager loading in your ORM.

There are no Dumb Questions

Q: Why not just store data in a JSON file?

Fine for tiny things. But a file can't safely handle many simultaneous writers, fast searches over millions of records, or crash-safety. Databases solve all three.

Q: What's an ORM?

A library that lets you use classes/objects instead of writing SQL by hand. Convenient, but understand the SQL it generates.

Q: What are migrations?

Versioned scripts that change your database structure (add a column) the same way for every developer and environment, like git for the schema.

✏️ Sharpen your pencil: write the SQL

Using the pets table: (1) list all dogs (2) change Tom's species to "lion" (3) count how many pets there are.
Answer:

SELECT * FROM pets WHERE species = 'dog';
UPDATE pets SET species = 'lion' WHERE name = 'Tom';
SELECT COUNT(*) FROM pets;

Key points
  • Databases keep data durable, searchable and safe under concurrency.
  • Tables + keys + JOINs model relationships without duplicating data.
  • Indexes make searches fast; transactions make multi-step changes all-or-nothing.
  • Always use parameterised queries to prevent SQL injection.

📋 Quick reference: the details

Key ideaA process's memory vanishes when it stops (module 1). A database is a separate program that stores data durably, lets many clients query it safely at once, and keeps it consistent.

Relational databases (SQL)

Data lives in tables (rows and columns) with a fixed schema. Tables relate via keys. Examples: PostgreSQL, MySQL, SQLite.

users:  id (PK) | name | email
orders: id (PK) | user_id (FK → users.id) | total | created_at

CREATE TABLE users (id SERIAL PRIMARY KEY, name TEXT NOT NULL, email TEXT UNIQUE);

INSERT INTO users (name, email) VALUES ('Ana', 'ana@example.com');
SELECT name, email FROM users WHERE id = 42;
UPDATE users SET name = 'Ana B' WHERE id = 42;
DELETE FROM users WHERE id = 42;

-- JOIN: combine tables
SELECT u.name, SUM(o.total) AS spent
FROM users u JOIN orders o ON o.user_id = u.id
GROUP BY u.name ORDER BY spent DESC LIMIT 10;
  • Primary key: unique row identifier. Foreign key: reference enforcing relationships.
  • Normalisation: store each fact once (don't copy the customer's address into every order).
  • Constraints (NOT NULL, UNIQUE, FK) keep bad data out.

Indexes

Like a book's index: without one the DB scans every row (O(n)); with a B-tree index on a column it finds rows in O(log n). Cost: extra storage and slower writes. Index columns used in WHERE, JOIN, ORDER BY. EXPLAIN shows the plan.

CREATE INDEX idx_orders_user ON orders (user_id);

Transactions and ACID

A transaction groups steps so they succeed or fail together (transfer money: debit + credit).

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;      -- or ROLLBACK on error
ACIDMeaning
AtomicityAll or nothing
ConsistencyConstraints always hold
IsolationConcurrent transactions don't see each other's half-finished work
DurabilityOnce committed, survives crashes

Using a database safely from code

  • SQL injection: never build queries by pasting user input into strings. Use parameterised queries. 
    # BAD:  cur.execute("SELECT * FROM users WHERE name = '" + name + "'")
# GOOD:
cur.execute("SELECT * FROM users WHERE name = %s", (name,))
  • An ORM (SQLAlchemy, Prisma) maps tables to objects; beware the "N+1 query" problem.
  • Migrations version your schema changes. Back up; test restores. Least-privilege DB accounts.
