7. Git and Version Control

A time machine and collaboration tool for code.

📁 Start here: "final_FINAL_v2_reallyfinal.doc"

A story You've written an essay. To be safe you save copies: essay.doc, essay_v2.doc, essay_FINAL.doc, essay_FINAL_edited.doc... Now your friend edits one copy while you edit another. Which is the real one? What did they change?

Git solves this. Instead of copies, it keeps a timeline of snapshots, each with a note on what changed and who changed it. You can jump back to any moment, compare any two, and merge two people's work together.

Think of commits as save points in a video game

  ●────●────●────●────●        ← main: each ● is a COMMIT (a snapshot + message)
  A    B    C    D    E
            \
             ●────●             ← feature branch: a side quest
             F    G

A commit is a saved snapshot with a message ("Add login page"). A branch is a separate line of commits so you can experiment without breaking the main game. When the side quest works, you merge it in.

The three boxes (the part everyone finds confusing)

Packing a moving box: first you choose what goes in the box, then you seal and label it, then you ship it.

  Your files      git add       Staging area     git commit     Repository      git push    GitHub
  (editing)  ─────────────►  (items chosen) ─────────────►  (history)  ─────────────►  (shared copy)

Your first 10 minutes

$ mkdir my-site && cd my-site
$ git init                           # start tracking this folder
$ echo "<h1>Hello</h1>" > index.html
$ git status                         # shows index.html as "untracked"
$ git add index.html                 # put it in the box
$ git commit -m "Add home page"      # seal + label it. Save point #1!
$ git log --oneline                  # your timeline
a1b2c3d Add home page

Now change the file and use git diff to see exactly what changed, then add + commit again.

Branching without fear

$ git switch -c dark-mode        # new branch (side quest)
  ...edit, add, commit...
$ git switch main                # back to the main timeline
$ git merge dark-mode            # bring the side quest in

Merge conflicts: when two people edit the same line

Ana (branch A)I changed the title to "Pizza Palace".

Ben (branch B)I changed that same line to "Best Pizza".

GitI can't guess who's right. You two sort it out!

<<<<<<< HEAD
<h1>Pizza Palace</h1>
=======
<h1>Best Pizza</h1>
>>>>>>> best-pizza

Open the file, keep what you want (delete the markers), git add, git commit. Done. Conflicts feel scary but are routine.

Brain powerWhy is it a bad idea to commit a file containing your database password, even if you delete it in the next commit? The old commit still has it in history; anyone with the repo can find it. Treat it as leaked, change the password.

Git vs GitHub

Git = the tool on your computer. GitHub (or GitLab) = a website that hosts copies of repositories so teams can share them and review each other's work through pull requests ("here are my changes, please review and merge").

  your laptop ── git push ──► GitHub ◄── git push ── teammate's laptop
              ◄── git pull ──        ──► git pull

There are no Dumb Questions

Q: Why the staging area? Why not commit everything?

So you can make clean commits. You edited 5 files but only 2 relate to the login fix. Stage those 2, commit "Fix login redirect", then handle the rest separately.

Q: I messed up. Can I undo?

Almost always. Discard edits: git restore file. Undo a commit safely: git revert <id>. Git's superpower is that committed work is very hard to lose.

Q: What should go in a commit message?

Short, in the imperative, saying what and why: "Fix crash when cart is empty". Not "stuff" or "update".

Q: What's .gitignore?

A list of files git should never track: secrets (.env), build output, node_modules.

✏️ Sharpen your pencil: order the steps

Put in order: git push, edit a file, git commit -m "...", git add.
Answer: edit → git add → git commit → git push.

Key points
  • Git = timeline of snapshots (commits), not copies of files.
  • Flow: edit → add (stage) → commit (save) → push (share).
  • Branches let you experiment safely; merge combines them. Conflicts are resolved by hand.
  • Git is the tool, GitHub is a hosting service. Never commit secrets.

📋 Quick reference: the details

Key ideaGit records snapshots (commits) of your project. Each commit has an ID, an author, a message and points to its parent, forming a history you can browse, compare, branch and merge.

Three areas

AreaWhat it isMove on
Working directoryYour files as edited nowgit add →
Staging area (index)Changes chosen for the next commitgit commit →
RepositoryPermanent history of commitsgit push → remote

Everyday workflow

git clone URL            # copy a repo
git status               # what changed?
git diff                 # see the changes
git add file.py          # stage
git commit -m "Fix login redirect"
git log --oneline        # history
git pull                 # fetch + merge remote changes
git push                 # publish your commits

Branches

A branch is a movable pointer to a commit, a cheap parallel line of work.

git switch -c feature/search    # create + move to branch
# ...commit work...
git switch main
git merge feature/search        # bring the work in
  • Merge conflict: two branches changed the same lines. Git marks them (<<<<<<<, =======, >>>>>>>); you edit to the right result, git add, commit.
  • Pull request (PR): on GitHub/GitLab, a request to merge your branch with review and discussion.

Good habits

  • Small, focused commits with messages saying why.
  • .gitignore keeps build output, node_modules and secrets (.env) out. A secret committed once stays in history; rotate it.
  • Undo: git restore file (discard edits), git revert <id> (new commit undoing an old one, safe for shared history). Avoid rewriting history that others have pulled.
  • Git ≠ GitHub: Git is the tool; GitHub is a hosting service.
