13. REST APIs, JSON and API Design

How programs (not just people) use the web.

🍔 Start here: the drive-through menu

A story A burger drive-through has a clear menu board and clear rules: say the item, say what you want done (order, change, cancel), get a receipt. You don't need to know how the kitchen works. The menu is the contract.

An API (Application Programming Interface) is a drive-through window for software. Another program "orders" data or actions without knowing how your code or database works inside.

A REST API is a drive-through with very tidy, predictable rules: things have names (nouns), actions use HTTP verbs.

The pattern: nouns in the URL, verbs in the method

Take a resource, like "users". Everything you can do follows the same shape:

  GET     /users          → list all users
  POST    /users          → create a new user          (body: JSON)
  GET     /users/42       → get user #42
  PATCH   /users/42       → change part of user #42
  DELETE  /users/42       → delete user #42
  GET     /users/42/orders→ the orders belonging to user #42

Learn this pattern once and you can guess how most APIs work.

One full conversation

  CLIENT                                          SERVER
  POST /users
  Content-Type: application/json
  {"name":"Ana","email":"ana@x.com"}   ──────►  validates, saves to database
                                       ◄──────  201 Created
                                                {"id":43,"name":"Ana","email":"ana@x.com"}

  GET /users/999                       ──────►  looks... not there
                                       ◄──────  404 Not Found
                                                {"error":"user not found"}

Try a real public API in your terminal (no signup needed):

$ curl https://jsonplaceholder.typicode.com/users/1
{ "id": 1, "name": "Leanne Graham", ... }

$ curl -X POST https://jsonplaceholder.typicode.com/posts \
    -H "Content-Type: application/json" \
    -d '{"title":"hello","body":"world","userId":1}'

Brain powerWhich of these API designs is better: GET /deleteUser?id=5 or DELETE /users/5? The second. A GET should never change data; web crawlers and prefetchers follow GET links and would delete users by accident!

Making an API pleasant to use

  • Pagination: /users?page=2&limit=50 instead of a million rows at once.
  • Filtering/sorting: /users?role=admin&sort=name.
  • Versioning: /v1/users, so improving it later won't break old apps.
  • Consistent errors: always the same shape: {"error":{"code":"invalid_email","message":"..."}}.
  • Documentation: OpenAPI/Swagger gives an interactive page listing every endpoint.
  • Authentication: usually a token: Authorization: Bearer <token>.

There are no Dumb Questions

Q: Is REST a technology I install?

No, it's a style, a set of conventions on top of HTTP. Nothing to download.

Q: What's the difference between PUT and PATCH?

PUT replaces the whole thing; PATCH changes just the fields you send.

Q: What is GraphQL then?

An alternative: one endpoint where the client describes exactly which fields it wants. Great for complex UIs; REST remains the common default.

Q: What happens if a phone retries a "pay" request after a timeout?

You could charge twice! Real APIs use an idempotency key: a unique ID with the request so the server recognises the retry and doesn't repeat the action.

✏️ Sharpen your pencil: design a Todo API

Write the request line for: list todos, add a todo, mark todo 7 as done, delete todo 7.
Answer: GET /todos, POST /todos, PATCH /todos/7 (body {"done": true}), DELETE /todos/7.

Key points
  • An API is a contract that lets programs talk to each other.
  • REST: URLs name things (/users/42), HTTP methods are the actions.
  • Exchange JSON; use accurate status codes and a consistent error format.
  • Paginate, version, document, and authenticate.

Design guidelines

  • Nouns, plural, lowercase in paths (/orders), not /getOrders.
  • Use the right status code: 400 invalid input, 401 not logged in, 403 not allowed, 404 missing, 409 conflict, 422 validation failed, 429 too many requests.
  • Consistent error shape: {"error": {"code": "invalid_email", "message": "..."}}.
  • Pagination for lists: GET /users?page=2&limit=50; also filtering and sorting by query parameters.
  • Versioning so you don't break clients: /v1/users.
  • Stateless: every request carries what the server needs (auth token). Idempotent PUT/DELETE can be safely retried.
  • Rate limiting and authentication (API keys, bearer tokens).
  • Document with OpenAPI/Swagger. Alternatives: GraphQL (client picks fields), gRPC (binary, typed).
