5. Authentication, Authorization, Sessions and Cookies

How a stateless protocol remembers who you are, and what you may do.

🎟️ Start here: the concert wristband

A story At a music festival, you show your photo ID at the gate. A guard checks it and snaps a wristband on you. After that, nobody asks for your ID again. They just glance at the wristband.

Inside, different colors open different doors: general = main stage, VIP = lounge, crew = backstage.

• Showing ID at the gate = authentication (who are you?)
• Wristband colour deciding which doors open = authorization (what may you do?)
• The wristband itself = a session / cookie (so you needn't show ID again)
  ┌─ GATE (login) ──────────────┐      ┌─ INSIDE ──────────────────────┐
  │ "username + password"       │      │ show wristband (cookie)        │
  │ ✓ verified → issue wristband│ ───► │ guard checks colour (role):    │
  └─────────────────────────────┘      │   VIP → lounge ✓  main ✓       │
         AUTHENTICATION                │   general → lounge ✗ (403)     │
                                       └───────────────────────────────┘
                                                 AUTHORIZATION

The problem cookies and sessions solve

Remember: HTTP forgets you after every request. Without a wristband you'd have to type your password on every single click. So:

  1. POST /login  {user: ana, password: ****}
  2. Server checks password ✓. Creates a SESSION in its memory:
         session "k9x2Q7..." → { user: ana, role: "member" }
  3. ← 200 OK
        Set-Cookie: session=k9x2Q7...; HttpOnly; Secure     (the wristband!)
  4. Browser now automatically adds to EVERY later request:
        Cookie: session=k9x2Q7...
  5. Server looks up "k9x2Q7..." → ah, it's Ana.
  6. Logout → server deletes the session; the wristband becomes worthless.

Cookie = the little piece of data stored in your browser. Session = what the server remembers about you. The cookie is only the claim ticket; the valuables stay in the server's cloakroom.

Brain powerA thief steals your wristband (session ID) without knowing your password. Can they get in? Yes! The guard only checks the wristband. That's "session hijacking", and why we use HTTPS, HttpOnly, Secure, and short lifetimes.

Authentication vs authorization: two real examples

Don't store passwords! Store a hash, a one-way scramble. At login, scramble the typed password the same way and compare. If a thief steals the database they get scrambles, not passwords. Use slow, salted hashes: bcrypt, Argon2. (Never plain text. Never MD5.)

Peek at your own cookies

Open any site you're logged in to: F12 → Application → Cookies. Find the long random string named something like session or sid. Notice the HttpOnly and Secure tick boxes. Don't share its value; it's your wristband.

There are no Dumb Questions

Q: Why not just store the user's name in the cookie?

Because users can edit cookies. Change user=ana to user=admin and you're admin. Store a long random ID that can't be guessed, and keep the real data on the server.

Q: Are cookies "tracking"?

Cookies are just a tool. Login cookies are essential. Other cookies (from ad networks) are used for tracking, which is why sites ask for consent.

Q: What are JWTs I keep hearing about?

A different kind of wristband: instead of an ID pointing to server memory, it's a signed note containing your details. The server checks the signature, no lookup needed. Trade-off: harder to cancel before it expires (module 17).

Q: Why does "Log in with Google" exist?

So you don't give every site a new password. Google verifies you and tells the site "yes, this is Ana". More in module 17.

✏️ Sharpen your pencil: authN or authZ?

(1) Scanning your fingerprint. (2) A teacher can edit grades but a student can only view them. (3) Entering a 6-digit code from your phone. (4) A blogger can delete only their own posts.
Answer: (1) authN, (2) authZ, (3) authN (second factor), (4) authZ (ownership rule).

Key points
  • Authentication: who are you? Authorization: what may you do? In that order.
  • HTTP is stateless; cookies + sessions give it memory.
  • The cookie holds only a random ID. The session data lives on the server.
  • Use HttpOnly, Secure, SameSite; always HTTPS.
  • Hash passwords with a slow, salted algorithm. Always check permissions on the server.

Authentication factors

  • Something you know (password), have (phone, hardware key), are (fingerprint).
  • MFA combines two or more factors.
  • Passwords must never be stored in plain text. Store a salted hash made with a slow algorithm (bcrypt, scrypt, Argon2). At login, hash the attempt and compare.

Authorization models

  • Role-based (RBAC): users have roles (admin, editor, viewer); roles have permissions.
  • Ownership: "you can edit your own posts". Forgetting this check is a very common bug (IDOR): changing /orders/17 to /orders/18 shows someone else's order.
  • Always enforce on the server. Hiding a button in the UI is not security.

Cookies

A cookie is a small piece of data the server asks the browser to store and send back on every later request to that site.

Server → Browser:  Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Lax; Max-Age=3600
Browser → Server:  Cookie: session=abc123       (on every request to that domain)
AttributePurpose
HttpOnlyJavaScript can't read it (limits theft via XSS)
SecureOnly sent over HTTPS
SameSiteRestricts cross-site sending (helps against CSRF)
Max-Age / ExpiresLifetime; without it, a session cookie dies when the browser closes
Domain / PathWhere the cookie applies

Cookies are also used for preferences and tracking, not only login.

Sessions

Key ideaA session is server-side memory of a logged-in user across requests. The cookie holds only a random session ID; the real data stays on the server.
  1. User posts username + password (over HTTPS).
  2. Server verifies, creates a session record: {id: "abc123", user: 42, expires: ...} in memory/Redis/DB.
  3. Server responds with Set-Cookie: session=abc123.
  4. Browser sends the cookie with each request; server looks up the ID → knows it's user 42.
  5. Logout or expiry deletes the record; the ID becomes useless.

Session cookie vs token (JWT)

Server-side sessionToken (e.g. JWT)
State livesOn the serverInside the signed token held by client
Revoke instantlyEasy (delete record)Hard (valid until expiry unless extra tracking)
ScalingNeeds shared storeServers need no lookup

The session ID must be long, random and unguessable. An attacker who steals it can impersonate the user (session hijacking), which is why HTTPS, HttpOnly, and expiry matter.

Other mechanisms you'll meet

  • Basic auth / API keys via the Authorization header.
  • OAuth 2 / "Login with Google": authorization delegated to another provider; OpenID Connect adds authentication on top.
