27. Software Design: Modularity, SOLID, Patterns, Code Review

Code is read far more than it is written. Design for the next person (often you).

🧰 Start here: the messy garage vs the organised workshop

A story Two people each own a garage full of tools.
🗑️ Garage A: everything piled together. Need a screwdriver? Dig for ten minutes. Move one box and three others fall over.
🧼 Garage B: labelled drawers, each tool in a logical place, a pegboard outline showing where it belongs. Find anything in seconds. Adding a new tool means just adding a hook.

Code gets read and changed far more often than it's written. Software design is about building Garage B, so the next change (probably made by you in six months) is easy and safe.

Messy vs tidy: one real example

# 😖 MESSY: one function does validation, tax, email, database, and printing
def process(o):
    if o["items"] == []: print("err"); return
    t = 0
    for i in o["items"]: t += i[1] * i[2] * 1.2     # what is 1.2? what's i[1]?
    db.execute("INSERT ...")
    smtp.send(o["email"], "Thanks!")
    print("done")

# 😊 TIDY: small named pieces, each easy to read and test
TAX_RATE = 0.20

def order_total(items):
    return sum(item.price * item.qty for item in items) * (1 + TAX_RATE)

def place_order(order, db, notifier):
    if not order.items:
        raise ValueError("order has no items")
    order.total = order_total(order.items)
    db.save(order)
    notifier.send(order.email, "Thanks for your order!")

What improved: names explain intent, "magic number" 1.2 got a name, each function has one job, and db and notifier are passed in. So in tests you can pass fakes. (That's dependency injection.)

Patterns: named, tested solutions

Others have faced your problem before and named the solution. Knowing the names helps you talk about design:

# STRATEGY: swap interchangeable behaviours behind one interface
class StandardShipping:  def cost(self, w): return 5
class ExpressShipping:   def cost(self, w): return 5 + 2 * w

def checkout(weight, shipping):        # works with ANY strategy
    return shipping.cost(weight)

checkout(3, StandardShipping())   # 5
checkout(3, ExpressShipping())    # 11   (add "DroneShipping" later without touching checkout!)
PatternOne-liner
FactoryOne place decides which object to create
Observer / pub-sub"Tell me when X happens" (many listeners)
AdapterA plug converter between incompatible interfaces
RepositoryHide database details behind a simple interface
SingletonExactly one instance (use rarely, it's hidden global state)
Brain powerAre design patterns something to apply to every program? No. They're vocabulary for recurring problems. Forcing a pattern where none is needed adds complexity (see YAGNI: "You Aren't Gonna Need It").

Code smells: hints that something's off

  • Functions longer than a screen; deeply nested ifs (use early returns).
  • Copy-pasted code (but don't abstract too early: wait for the 3rd repeat, "rule of three").
  • Mysterious names: d, tmp2, process().
  • Functions with 6+ parameters or boolean flags that change behaviour.
  • Comments explaining confusing code (rewrite the code instead).

Refactoring = improving structure without changing behaviour, with tests as your safety net. Technical debt = shortcuts taken now that cost interest later. Borrow on purpose; repay regularly.

Code review: a conversation, not a trial

Weak"This is wrong."

Strong"What happens if the cart is empty here? I think sum() returns 0 but len() would be a divide-by-zero on line 12. Could we add a guard?"

  • Authors: small PRs, good descriptions, tests included, self-review first, welcome feedback.
  • Reviewers: check correctness, edge cases, security, clarity, tests. Ask questions, suggest, be kind. Review the code, never the person.
  • Let formatters/linters handle style so humans discuss design.

There are no Dumb Questions

Q: How do I know if a function is "too big"?

If you can't describe it in one short sentence without "and", split it. If you can't name it clearly, it probably does too much.

Q: Is object-oriented design required?

No. These ideas (cohesion, coupling, clarity) apply to functions, modules and services, in any paradigm.

Q: Shouldn't I design everything perfectly upfront?

No. Start simple, keep things easy to change, refine as you learn what the real requirements are.

def f(a, b): return a * b * 0.18 + a What are 3 improvements?
Answer: a descriptive name (price_with_tax), meaningful parameters (price, quantity), a named constant for 0.18 (TAX_RATE), and clearer formula/order. Also consider a docstring or a test.

Key points
  • Aim for high cohesion, low coupling; code is read more than written.
  • Name things well, keep functions small, avoid magic numbers, inject dependencies.
  • SOLID and patterns are vocabulary and guidance; use when needed, not for show.
  • Refactor with tests; manage technical debt; review code kindly and specifically.

📋 Quick reference: the details

Key ideaGood design makes change cheap. Split a system into parts with high cohesion (each part does one related thing) and low coupling (parts depend on each other as little as possible).

Core principles

  • Abstraction: hide details behind a simple interface (you call send_email(), not SMTP bytes).
  • Encapsulation: keep internal data private; expose a small public API.
  • DRY: don't repeat knowledge. But don't force abstraction on coincidentally similar code.
  • KISS / YAGNI: keep it simple; don't build what you don't need yet.
  • Separation of concerns: UI, business rules and data access in different places (module 19).
  • Composition over inheritance: build from small parts rather than deep class hierarchies.

Patterns are vocabulary, not goals. Use one when the problem appears, not to look sophisticated.

Readable code

  • Names reveal intent (days_until_expiry not d). Small functions. Avoid deep nesting (early returns). No magic numbers: name constants.
  • Code smells: long functions, duplicated code, giant classes, many parameters, boolean flags that change behaviour, comments explaining confusing code (rewrite the code).
  • Refactoring: change structure without changing behaviour, backed by tests (module 20). The "boy scout rule": leave code cleaner than you found it.
  • Technical debt: shortcuts that speed now and slow later. Take it consciously, and repay it.

Code review

  • Goals: catch bugs, share knowledge, keep standards, not to show off or police.
  • Authors: small PRs, clear description, self-review, tests, respond kindly.
  • Reviewers: check correctness, edge cases, security, readability, tests; ask questions; suggest, don't command; comment on code, not the person; approve when good enough, not perfect.
  • Automate nitpicks (formatters, linters) so humans discuss design.
