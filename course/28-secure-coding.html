28. Secure Coding: OWASP Top 10, Validation, Secrets

Assume someone is actively trying to break your app, because someone is.

🏦 Start here: the bank vault

A story A bank doesn't rely on one lock. It has a locked front door, guards, cameras, a vault with a time-lock, dye packs in the cash, and each employee only has keys to what they need. If one layer fails, others still protect the money. And the bank assumes someone will try to rob it.

Secure coding is the same mindset. Assume someone is actively trying to break your app (they are: bots probe new sites within minutes). Build in layers.

Four rules that prevent most disasters

  1. NEVER TRUST INPUT         everything from users/clients/other systems is "dirty" until checked
  2. LEAST PRIVILEGE           every account/service gets only the access it truly needs
  3. DEFENCE IN DEPTH          multiple layers; assume any one can fail
  4. FAIL SAFELY               errors should deny access and reveal nothing, not open the door

CIA triad: protect Confidentiality (only the right people read it), Integrity (nobody alters it improperly), Availability (it works when needed).

Attack tour #1: Injection (data becomes code)

Whenever user input is glued into a command, an attacker can sneak in their own commands.

# 😱 Command injection
host = request.args["host"]           # attacker sends:  8.8.8.8; cat /etc/passwd
os.system("ping -c1 " + host)         # runs BOTH commands!

# ✅ pass arguments as a list, no shell involved
subprocess.run(["ping", "-c1", host], check=True)

# 😱 SQL injection (module 18)  →  ✅ parameterised queries
# 😱 XSS (module 14)            →  ✅ escape output / textContent

Pattern: keep data and code separate. Use APIs that treat input strictly as data.

Attack tour #2: Broken access control (the #1 real-world flaw)

  You're logged in as user 17, viewing   /invoices/1042   (yours)
  You change the URL to                   /invoices/1043   (someone else's)  ← server returns it!

Logging in isn't enough; the server must check "does THIS user own THIS thing?" on every request, deny by default, and never rely on hiding buttons in the UI.

Validate input: the bouncer at the door

def create_user(data):
    email = data.get("email", "")
    age   = data.get("age")
    if not isinstance(email, str) or len(email) > 254 or "@" not in email:
        raise ValueError("invalid email")
    if not isinstance(age, int) or not (0 <= age <= 130):
        raise ValueError("invalid age")
    ...
  • Check type, length, range, format. Prefer allow-lists ("only these characters") over block-lists.
  • Always on the server; client-side checks are for convenience only.
  • File uploads: limit size, check real type, random filenames, store outside the web root.

The supply chain: you ship other people's code too

A typical app is ~90% third-party libraries. A vulnerability in one becomes your vulnerability.

  • Run npm audit / pip-audit / Dependabot; update regularly.
  • Pin versions with lock files; prefer well-maintained packages; beware look-alike names (reqeusts).
  • Protect your CI and deploy keys too.

SSRF: tricking your server into fetching secrets

Your app has a "fetch this image URL" feature. The attacker supplies http://169.254.169.254/..., an internal cloud metadata address, and your server cheerfully fetches its own credentials for them. Defence: allow-list destinations; block internal address ranges.

Brain powerA login page says "No account with that email" for unknown emails and "Wrong password" for known ones. What does this give an attacker? A way to find which emails have accounts (user enumeration). Use one generic message: "Email or password incorrect."

Security habits checklist

  • Rate-limit logins and expensive endpoints; lock out brute force.
  • Security headers: Strict-Transport-Security, Content-Security-Policy, X-Content-Type-Options.
  • Don't invent your own crypto; use vetted libraries.
  • Log security events (failed logins, permission denials) and monitor them (module 26).
  • Threat model early: ask "What could go wrong? Who'd attack? What would they gain?"
  • If you find a vulnerability in someone's system, report it responsibly; don't exploit it.

There are no Dumb Questions

Q: Is my small app really a target?

Yes. Attacks are automated: bots scan the whole internet for known flaws, default passwords and leaked keys. Size doesn't protect you.

Q: Isn't HTTPS enough?

It protects data in transit only. It does nothing about SQL injection, broken access control, weak passwords or leaked keys.

Q: What's the OWASP Top 10?

A regularly updated list of the most common serious web-app risks (injection, broken access control, misconfiguration, vulnerable components…). Great checklist to review your apps against.

✏️ Sharpen your pencil: find the flaws 

@app.get("/download")
def download():
    name = request.args["file"]
    return open("/var/app/uploads/" + name).read()
What's wrong?
Answer: path traversal: ?file=../../etc/passwd reads any file. Also no access check on who owns the file and no size/type limits. Fix: resolve and verify the path stays inside the uploads folder, use IDs instead of filenames, check ownership.

Key points
  • Never trust input; validate on the server; keep data separate from code (parameterise, escape).
  • Always check who may do what on every request; deny by default.
  • Least privilege, layered defences, safe failure, generic errors.
  • Protect secrets and dependencies; scan and update.
  • Think like an attacker (threat-model) and monitor for abuse.

Input validation

  • Validate on the server: type, length, range, format. Prefer allow-lists (what's permitted) over deny-lists.
  • Then encode for the output context (HTML, SQL, shell, URL).
  • File uploads: limit size, check type by content, store outside the web root, random names.
  • Command injection example: 
    # BAD:  os.system("ping " + host)         # host = "x; rm -rf /"
# GOOD: subprocess.run(["ping", "-c1", host], check=True)   # no shell

Habits

  • Least privilege: DB user can't drop tables; service has only the cloud permissions it needs.
  • Secrets out of code/logs/git (module 23). Rotate.
  • Keep dependencies updated; run npm audit / pip-audit / Dependabot. Supply-chain attacks target packages you trust.
  • Rate limit and add lockouts for login and expensive endpoints.
  • Error handling: show users a generic message; log details privately; no stack traces to clients.
  • Security headers: Strict-Transport-Security, Content-Security-Policy, X-Content-Type-Options.
  • Threat modelling: ask "what can go wrong? who would attack? what do they gain?" (STRIDE). Responsible disclosure: report found bugs to owners, never exploit without permission.
  • Don't roll your own crypto; use vetted libraries.
