4. HTTP, HTTPS, Requests, Responses and a Simple Server

The language browsers and servers use to talk.

🍽️ Start here: the restaurant

A story At a restaurant you (the client) tell the waiter what you want. The waiter goes to the kitchen (the server) and returns with either your food or an apology: "Sorry, we're out of that."

Key rules of this restaurant:
• You must ask first. The kitchen never sends food unprompted.
• The waiter has no memory. Every order starts with "Hi, table 5, I'd like..." (this is stateless).
• Every answer has a clear outcome: here's your food / we don't have that / the kitchen is on fire.

That's HTTP: a request, a response, a status code that says how it went.

A request, line by line

  GET /menu?vegan=true HTTP/1.1      ← METHOD  PATH?query  VERSION
  Host: pizza.example.com            ← which restaurant (headers: extra info)
  Accept: text/html                  ← "I'd like HTML please"
  Cookie: table=5                    ← "I'm table 5" (remember me!)
                                     ← blank line, then optional BODY
MethodRestaurant version
GET"Show me the menu." (just looking, changes nothing)
POST"Here's my order." (creates something new)
PUT / PATCH"Change my order." (replace / modify)
DELETE"Cancel my order."

A response, line by line

  HTTP/1.1 200 OK                    ← STATUS: how did it go?
  Content-Type: text/html            ← what you're getting
  Content-Length: 1234
                                     ← blank line
  <html> ...the page... </html>      ← BODY

Status codes by first digit, so you can read them like traffic lights:

2xx 🟢"Done!" (200 OK, 201 Created)
3xx 🔀"Go over there instead." (301/302 redirect)
4xx 🟠You messed up. (404 not found, 403 not allowed, 400 bad request)
5xx 🔴We messed up. (500 crashed, 503 overloaded)

Brain powerA page with 1 HTML file, 3 images, 2 CSS files and 4 scripts: how many HTTP requests? (10. The browser asks for the HTML, finds out what else it needs, then asks again for each one.)

HTTPS: the sealed envelope

Plain HTTP is a postcard: anyone handling it can read it (café Wi-Fi owner, your ISP). HTTPS puts it in a sealed, tamper-proof envelope, and checks the address is really the place you meant.

  Browser                                   Server
     │ ── "hello, I speak these ciphers" ──►  │
     │ ◄── certificate (ID card from a CA) ── │   ① "I'm really example.com"
     │  checks: name matches? not expired?    │   ② browser verifies the ID
     │      signed by someone I trust?        │
     │ ◄───── agree on a secret key ─────►    │   ③ both now share a secret
     │ ═══ everything now encrypted ═══════   │   ④ HTTP flows inside the tunnel

A certificate is like a passport; a Certificate Authority (CA) is the government that issued it, trusted by your browser.

Build your own server (the "aha" moment)

Save as server.py, run python3 server.py, then visit http://localhost:8000:

from http.server import BaseHTTPRequestHandler, HTTPServer

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):                    # called for every GET request
        print("Request for:", self.path)  # watch your terminal!
        body = f"You asked for {self.path}".encode()
        self.send_response(200)           # status line
        self.send_header("Content-Type", "text/plain")
        self.end_headers()                # the blank line
        self.wfile.write(body)            # the body

HTTPServer(("127.0.0.1", 8000), Handler).serve_forever()

Visit /pizza, then /anything. Your terminal prints each request. That's all a web server is: a process looping forever, waiting for requests and writing responses. Django, Flask, Express: all just fancier versions.

There are no Dumb Questions

Q: If HTTP forgets everything, how does a shop remember my cart?

Your browser sends a small ID with each request (a cookie), and the server looks the ID up. The waiter has no memory, but he's holding your table number. (More in the next module.)

Q: 401 vs 403, what's the difference?

401: "I don't know who you are, log in." 403: "I know who you are, and you're not allowed."

Q: Does the padlock mean the site is safe?

It means the connection is private and you're talking to the real owner of that domain. A scam site can have a padlock too. Always check the domain name.

✏️ Sharpen your pencil: read the status

What went wrong in each? (a) 404 (b) 500 (c) 301 (d) 503 (e) 403
Answer: (a) client asked for something that doesn't exist; (b) server code crashed; (c) page moved permanently, follow the new address; (d) server overloaded or down for maintenance; (e) you're known but forbidden.

Key points
  • HTTP = client sends a request (method, path, headers, body), server returns a response (status, headers, body).
  • It's stateless; memory comes from cookies/sessions.
  • Status first digit: 2 ok, 3 redirect, 4 your fault, 5 server's fault.
  • HTTPS = HTTP inside TLS: privacy, tamper-proofing, and proof of identity via certificates.
  • A web server is a long-running process that loops: accept, read request, write response.

📋 Quick reference: the details

Key ideaHTTP is a text-based request → response protocol over TCP. The client asks; the server answers. Each request is independent (stateless).

Request

GET /products?id=42 HTTP/1.1
Host: shop.example.com
Accept: text/html
Cookie: session=abc123

(optional body)
  • Method: what to do. GET read, POST create/submit, PUT/PATCH update, DELETE remove.
  • Path + query string: which resource, plus parameters (?id=42).
  • Headers: metadata (Host, Content-Type, Authorization, Cookie).
  • Body: data sent (form fields, JSON), mostly with POST/PUT.

Response

HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1234
Set-Cookie: session=abc123; HttpOnly

<html>...</html>
StatusMeaningCommon
1xxInformational101
2xxSuccess200 OK, 201 Created, 204 No Content
3xxRedirect301 Moved, 302 Found, 304 Not Modified
4xxClient's fault400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found
5xxServer's fault500 Internal Error, 502 Bad Gateway, 503 Unavailable

Safe vs idempotent

Safe = doesn't change server state (GET). Idempotent = repeating gives same result as doing once (GET, PUT, DELETE; POST is not). Never use GET for actions that change data.

HTTPS

Key ideaHTTPS = HTTP inside a TLS encrypted tunnel. It gives confidentiality (nobody on the path can read it), integrity (can't be modified undetected) and authentication of the server (you're talking to the real site).
  1. Client connects to port 443 and says hello with supported ciphers.
  2. Server sends its certificate (contains its public key, signed by a trusted Certificate Authority).
  3. Client verifies the certificate (domain matches, not expired, signed by a trusted CA).
  4. They agree on a shared session key (asymmetric crypto to agree, then fast symmetric crypto for the data).
  5. HTTP requests now travel encrypted.

Without HTTPS, anyone on the Wi-Fi or any hop can read passwords and cookies. HTTPS does not hide which domain you visit (visible via DNS/SNI) and does not mean the site is trustworthy, only that the connection is private and the site owns the domain.

A simple HTTP server

Remember: it's just a process listening on a port, parsing requests and writing responses.

Python (standard library)

# server.py
from http.server import BaseHTTPRequestHandler, HTTPServer

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path == "/":
            body = b"<h1>Hello, class!</h1>"
            self.send_response(200)
        else:
            body = b"Not found"
            self.send_response(404)
        self.send_header("Content-Type", "text/html")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)

HTTPServer(("127.0.0.1", 8000), Handler).serve_forever()
python3 server.py
curl -i http://localhost:8000/         # 200
curl -i http://localhost:8000/nope     # 404

Node.js

// server.js
const http = require("http");
http.createServer((req, res) => {
  res.writeHead(200, {"Content-Type": "text/plain"});
  res.end("Hello from " + req.url + "\n");
}).listen(8000);
