16. Proxies, Reverse Proxies, Load Balancers, CDNs and Caching

What sits between the browser and your code, and why.

🏬 Start here: the popular shop

A story Ana's tiny bakery becomes famous. Problems appear:
😰 One counter, a line down the street. → Open more counters and a person at the door directs customers: that's a load balancer.
😰 Customers keep asking the baker the same question ("Do you have sourdough?"). → Put a sign in the window: a cache.
😰 Customers across the country wait days for deliveries. → Open branch shops in each city stocked with the popular items: a CDN.
😰 The baker wants a receptionist who greets everyone, turns away troublemakers and sends people to the right department: a reverse proxy.

Reverse proxy: the receptionist

A program like Nginx or Caddy sits in front of your app. It can:

  • Handle HTTPS so your app doesn't have to.
  • Route: /api/* → backend app; everything else → static files.
  • Compress responses, add security headers, rate-limit abusers.
# Tiny Nginx config
server {
  listen 443 ssl;
  server_name shop.example.com;
  location /api/ { proxy_pass http://localhost:8000; }   # to the app
  location /     { root /var/www/site; }                  # static files
}

Forward vs reverse: a forward proxy hides clients (a VPN or school filter). A reverse proxy hides servers.

Load balancer: the door person

Many identical servers; the balancer picks one per request (round-robin, least busy…). It also runs health checks: if server 2 stops answering, it's removed from rotation and nobody notices. This gives both scale and availability.

Gotcha: if "who is logged in" is stored in one server's memory, the next request may land on a different server that has never heard of you, so you're suddenly logged out. Fix: keep servers stateless and store sessions in a shared place (Redis or database).

CDN: branch shops everywhere

A Content Delivery Network keeps copies of your images, CSS and JS on servers around the world. A user in Mumbai gets files from Mumbai instead of from your server in Virginia, cutting delay. (Physics: signals take time to travel.)

Caching: the sign in the window

Doing work once and remembering the answer. Caches exist at every level:

  Browser cache → CDN → Reverse proxy → App cache (Redis) → Database
  (closest to user = fastest)                     (furthest = slowest)
Cache-Control: max-age=86400        # "this is good for 1 day, don't ask again"
Cache-Control: no-store             # "never keep a copy" (private data!)
ETag: "v42"  →  next time browser sends  If-None-Match: "v42"
             →  server: 304 Not Modified (no body: "yours is still fine")

The hard part: invalidation

If the baker's sign says "sourdough available" but it sold out, customers are misled. Caches go stale. Solutions:

  • TTL: entries expire after a set time.
  • Cache busting: name files by content: app.3f9a1c.js. New version = new name, so you can cache old names for a year.
  • Purge: tell the CDN/cache to forget something now.
Brain powerYou uploaded a new logo with the same filename, but users still see the old one. List every place the old one might be hiding. Their browser cache, the CDN, the reverse proxy, your app's cache. Fix with versioned filenames or a purge.

There are no Dumb Questions

Q: Isn't the load balancer itself a single point of failure?

Yes, so in practice it's duplicated too, usually provided as a managed service (cloud load balancers are redundant by design).

Q: How does my app know the user's real IP behind a proxy?

The proxy adds it in a header (X-Forwarded-For). Trust that header only when it comes from your own proxy.

Q: Which things should never be cached publicly?

Anything personalised (account pages, private data). Mark them private or no-store.

✏️ Sharpen your pencil: which tool?

(1) Serve images faster to a worldwide audience. (2) Spread traffic over 5 identical servers. (3) Terminate HTTPS and route /api to a backend. (4) Avoid re-running the same expensive database query.
Answer: (1) CDN, (2) load balancer, (3) reverse proxy, (4) cache (e.g. Redis).

Key points
  • Reverse proxy = front door (HTTPS, routing, compression, protection).
  • Load balancer = spreads requests over many servers and avoids failed ones.
  • Stateless servers make scaling easy; share session state externally.
  • CDN puts content near users; caching reuses work at every layer.
  • Invalidation is the hard part: TTLs, versioned filenames, purges.

A reverse proxy commonly: terminates HTTPS, routes /api to one service and / to another, compresses, rate-limits, adds security headers, and serves static files. The real client IP then arrives in the X-Forwarded-For header.

Load balancers

Spread requests across several identical servers for capacity and availability: if one dies, traffic goes to the others.

  • Algorithms: round-robin, least connections, hash by client.
  • Health checks remove broken servers from rotation.
  • Sticky sessions pin a user to one server. Better: keep servers stateless and store sessions in a shared store (module 5).
  • Horizontal scaling (more machines) vs vertical (bigger machine).

CDN: Content Delivery Network

A worldwide network of edge servers caching your static files (images, JS, CSS, video) close to users. Lower latency (physics: distance matters), less load on your origin, DDoS absorption. DNS or anycast routing directs users to the nearest edge.

Caching

Store a copy to avoid redoing expensive work. Layers: browser → CDN → reverse proxy → application cache (Redis) → database.

Cache-Control: public, max-age=86400        # cache a day
Cache-Control: no-store                     # never cache (sensitive)
ETag: "v123"   →  client sends  If-None-Match: "v123"
                  server replies 304 Not Modified (no body)
  • Cache hit/miss, TTL (how long valid), invalidation (when data changes).
  • "There are only two hard things in computer science: cache invalidation and naming things."
  • Cache busting: filenames with a content hash (app.3f9a1c.js) so new versions load immediately and old ones can be cached for a year.
  • Never cache personalised or private responses in shared caches (private/no-store).
