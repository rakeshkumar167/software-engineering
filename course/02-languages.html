2. Interpreted vs Compiled Languages

The CPU only understands machine code. Every language needs a way to get there.

🗣️ Start here: the translator problem

A story The CPU is a very fast worker who only speaks machine code (long strings of 1s and 0s). You speak Python or C or JavaScript. You need a translator.

There are two kinds of translators:
📖 The book translator (compiler): you hand over your whole book. They translate it completely and give you back a finished book in the other language. Later, anyone can read it without the translator.
🎧 The live interpreter: they sit next to you and translate every sentence as you speak. No finished book, but you can start talking immediately. And you must bring them along every time.
  COMPILED                              INTERPRETED
  hello.c ──[compiler]──► hello (binary)    hello.py ──► [interpreter] ──► runs
  (translate ONCE, run many times)          (translate WHILE running, every time)
  ./hello  ← runs alone                     python3 hello.py ← needs python installed

See the difference with the same bug

Here's the same mistake in both worlds. We call a function that doesn't exist, but only in a rarely-used branch:

# Python (interpreted)
def checkout(cart, coupon):
    if coupon:
        apply_discont(cart, coupon)   # typo! "discont"
    return sum(cart)

checkout([5, 10], None)   # works fine!  The typo line never ran.
checkout([5, 10], "SAVE") # 💥 NameError, found only NOW, in front of a customer

A compiler (like Go or Rust) would have refused to build the program and pointed at that line before anyone ran it. That's the big trade: compiled = problems caught early, interpreted = fast to try.

Brain powerYou're writing a quick script to rename 500 photos, you'll run it once. Compiled or interpreted? And if you were building the software that controls a pacemaker? (Script → interpreted, speed of writing wins. Pacemaker → compiled and strongly typed, catching mistakes early wins.)

The middle ground (most real languages)

  Java:    .java ─compile─► bytecode ─► [JVM runs it, JIT makes hot parts fast]
  Python:  .py   ─compile─► bytecode (.pyc) ─► [Python VM interprets]
  JS (V8): source ─► interpreted at first ─► busy functions get compiled on the fly (JIT)

Bytecode is a half-translated, portable language. A VM (virtual machine) runs it on any computer. JIT = "Just-In-Time": watch what runs a lot, and compile just that for speed.

There are no Dumb Questions

Q: So which is "better"?

Neither. It's like asking if a truck or a bicycle is better. Pick for the job: games, databases, operating systems often compile; scripts, web backends, data analysis often interpret.

Q: Why do I have to install Python to run a Python program but not a .exe?

The .exe is already translated, the translator isn't needed. A .py file is raw text; Python is the live interpreter that must be present.

Q: Is my browser's JavaScript interpreted?

Started that way; modern engines mix interpreting with JIT compiling, so it's fast. "Interpreted vs compiled" is about how a language is run, not a fixed label on the language.

✏️ Sharpen your pencil: who needs what?

You email a friend (who has a fresh laptop, no developer tools) your program. For each, can they run it? (1) a compiled hello.exe for their OS, (2) hello.py, (3) a .jar file.
Answer: (1) Yes. (2) No, they must install Python first. (3) Only if they have Java (the JVM) installed.

Key points
  • CPUs only understand machine code; every language needs translating.
  • Compiler = translate everything first. Interpreter = translate while running.
  • Compiled catches many errors early and runs fast. Interpreted is quick to edit and try.
  • Bytecode + VM + JIT blur the line; look at the implementation, not just the language.

📋 Quick reference: the details

Key ideaA compiler translates the whole program to machine code before it runs. An interpreter reads and executes the program while it runs.
Compiled (C, C++, Go, Rust)Interpreted (Python, Ruby, JavaScript*, PHP)
StepsSource → compile → executable → runSource → interpreter runs it directly
SpeedUsually faster at runtimeUsually slower at runtime
ErrorsMany caught at compile timeMany appear only when that line executes
DistributionShip the binary (per OS/CPU)Ship source; user needs the interpreter
Dev loopEdit → compile → run (slower feedback)Edit → run (fast feedback)
PortabilityRebuild per platformSame source runs wherever the interpreter exists

It's a spectrum, not two boxes

  • Bytecode + VM: Java compiles to bytecode, run by the JVM. Python also compiles to bytecode (.pyc) then interprets it.
  • JIT (Just-In-Time): engines like V8 (Chrome/Node.js) compile hot code to machine code while running, so "interpreted" JavaScript can be quite fast.
  • Languages aren't inherently one or the other; it's about the implementation.
  • Static vs dynamic typing is a separate axis (TypeScript is typed but compiles to JavaScript).

See it

# Compiled
gcc hello.c -o hello    # compile
./hello                 # run the binary

# Interpreted
python3 hello.py        # interpreter reads + runs source
node hello.js
Why it matters: a deployed Python/Node server needs the runtime installed (this is a big reason for containers); a Go server is a single binary you copy to the machine.
