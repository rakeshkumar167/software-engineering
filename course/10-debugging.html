10. Debugging and Reading Error Messages

Finding out why the program does not do what you think it does.

🔍 Start here: the detective

A story A detective doesn't randomly accuse people. They look at the scene, list suspects, test each theory against the evidence, and eliminate until one explanation fits.

Debugging is the same job. Your program's "crime" is that it doesn't do what you expected. A bad programmer changes code randomly and hopes. A good one investigates.

The 6-step detective method

  1. REPRODUCE   ─ make the bug happen on demand
  2. READ        ─ read the error message fully (clues!)
  3. NARROW      ─ where does it start going wrong? (cut the search area in half)
  4. HYPOTHESIS  ─ "I think X is None here" → test it (print / debugger)
  5. FIX         ─ fix the CAUSE, not the symptom
  6. PROTECT     ─ add a test so it can't sneak back

Case file #1: reading a stack trace

Traceback (most recent call last):
  File "shop.py", line 22, in <module>
    print(average_price(cart))
  File "shop.py", line 9, in average_price
    return sum(prices) / len(prices)
ZeroDivisionError: division by zero

Step 1: read the LAST line firstZeroDivisionError. Something divided by zero.

Step 2: find the nearest line in YOUR codeshop.py line 9: len(prices) must be 0.

Step 3: ask "how did we get here?"Line 22 called it with an empty cart!

FixHandle the empty cart: if not prices: return 0.

Case file #2: the sneaky logic bug (no error at all!)

def is_adult(age):
    return age > 18      # Bug: 18-year-olds are adults too!

No crash, just wrong answers. Logic bugs don't announce themselves. You find them by checking your assumptions: print the value, try the edge cases (17, 18, 19), compare with what you expected.

Debugging mindset

  • It's never "the computer is broken". The computer does exactly what the code says. Find the gap between what you think the code says and what it actually says.
  • Change one thing at a time, or you won't know what helped.
  • Search the exact error message. Thousands have hit it before you.
  • Take a break. Surprisingly effective.

There are no Dumb Questions

Q: Is print debugging "unprofessional"?

No! Everyone uses it. Debuggers are better for complex cases, but a well-placed print is often the fastest clue.

Q: What is the difference between a bug and an error?

An error is when the program complains. A bug is any behaviour that doesn't match what was intended. Some bugs raise errors; the nastiest ones don't.

Q: Why do I need a test after I fixed the bug?

Because bugs return when someone changes the code later. A test is a permanent alarm for this exact mistake.

✏️ Sharpen your pencil: find the bug 

def average(nums):
    total = 0
    for n in nums:
        total += n
    return total / len(nums) + 1
The average of [2, 4] is printing 4.0 but should be 3.0. What's the bug and how would you find it?
Answer: a stray + 1 at the end. Find it by printing total and len(nums) (6 and 2, so 3.0 is right so far), which shows the extra step is the faulty one. Then add a test: assert average([2,4]) == 3.

Key points
  • Debugging = investigation: reproduce, read, narrow, hypothesise, fix, protect.
  • Read stack traces from the last line up; find the first frame in your code.
  • Logic bugs have no error. Check assumptions with prints, breakpoints, edge cases.
  • Fix root causes, change one thing at a time, add a regression test.

📋 Quick reference: the details

Key ideaDebugging is the scientific method: observe, form a hypothesis, test it, repeat. Guessing and changing random things is the slow path.

A repeatable process

  1. Reproduce the bug reliably. If you can't trigger it, you can't know you fixed it.
  2. Read the error fully. Message says what; stack trace says where.
  3. Narrow down: which input, which function, which commit? Bisect: cut the problem space in half repeatedly (git bisect does this over history).
  4. Form a hypothesis and test it with a print, a log line, a debugger or a tiny test.
  5. Fix the cause, not the symptom.
  6. Add a test so it never returns.

Reading a stack trace

Traceback (most recent call last):
  File "app.py", line 20, in <module>
    print(average([]))
  File "app.py", line 12, in average
    return sum(xs) / len(xs)
ZeroDivisionError: division by zero

Read the last line first (the error type and message), then the nearest frame in your code (line 12). The frames above show how you got there. Search the exact error message; most errors have been met before.

Tools

  • Print / log debugging: quick; print values and which branch ran.
  • Debugger: set a breakpoint, pause, inspect variables, step line by line (VS Code, pdb, browser DevTools).
  • Browser DevTools: Console (errors), Network (requests/responses), Elements.
  • Rubber duck: explain the code out loud, line by line. Often reveals the flaw.
