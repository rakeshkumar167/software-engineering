23. Environments and Configuration: Dev, Staging, Prod, Secrets

Same code, different places it runs.

🎭 Start here: the theatre play

A story A theatre company performs the same play (your code) in different places:
🎒 In the rehearsal room (development), actors wear casual clothes, props are cardboard, a director stops them to fix mistakes.
🎟️ At the dress rehearsal (staging), everything is exactly like opening night, but only staff attend.
🌟 On opening night (production), the real set, real audience, no stopping.

The script never changes. Only the setting does: which theatre, which props, which keys to the building. That setting is configuration. Keeping config separate from code lets the same code run safely everywhere.
  SAME CODE ─┬─► dev      DATABASE_URL=sqlite:///dev.db       DEBUG=true   (fake data)
             ├─► staging  DATABASE_URL=postgres://staging-db  DEBUG=false  (copy-like data)
             └─► prod     DATABASE_URL=postgres://prod-db     DEBUG=false  (REAL customers)

Why not just hard-code the values?

# ❌ BAD: password in the code. It's in git forever, readable by everyone with repo access
db = connect("postgres://admin:SuperSecret123@prod-db.example.com/shop")

# ✅ GOOD: read from the environment at runtime
import os
db = connect(os.environ["DATABASE_URL"])     # crashes immediately if missing (good! fail fast)

Environment variables are named values the OS hands to a process when it starts (module 1 & 6). Set them in the shell, a .env file, your hosting platform's settings page, or a secrets manager.

$ export DATABASE_URL="postgres://..."
$ python app.py                     # app now sees DATABASE_URL

The .env file pattern

  .env            ← real values for YOUR laptop.  ✋ in .gitignore, NEVER committed
  .env.example    ← the same keys with fake values. ✅ committed, so teammates know what to set

  # .env.example
  DATABASE_URL=postgres://user:password@localhost/shop
  STRIPE_KEY=sk_test_xxx
  DEBUG=true

Secrets: treat them like house keys

Real story: developers accidentally push an AWS key to a public repo; bots scan GitHub constantly and use it to mine cryptocurrency within minutes, running up huge bills. Deleting the file afterwards doesn't help (git remembers). Rotate (replace) the key at once.
  • Secrets = passwords, API keys, tokens, signing keys, database URLs.
  • Never in git, screenshots, chat, logs, or browser JavaScript (anything the browser gets is public!).
  • Production secrets live in a secrets manager or the platform's encrypted settings.
  • Least privilege: a key should only do what that service needs.
  • Different secrets per environment; a leaked dev key mustn't unlock production.

Same dependencies everywhere

"Works on my machine" often means library versions differ. Fix with:

  • A dependency list (requirements.txt, package.json) plus a lock file pinning exact versions.
  • Isolated environments per project (Python venv, Node's node_modules) or containers (next module).
  • A README with a one-command setup.

Feature flags: light switches for new features

if flags.is_enabled("new_checkout", user):
    return new_checkout_page()
return old_checkout_page()

Deploy the code with the feature off, then turn it on for staff, then 5% of users, then everyone, and instantly off again if something's wrong. No redeploy.

Brain powerA bug appears only in production. What differences between environments could explain it? Library/runtime versions, config values and flags, real data volume and weirdness, OS, network setup (proxy/CDN/TLS), permissions, load, time zone.

There are no Dumb Questions

Q: Isn't a config file in the repo easier?

For non-secret defaults, yes. But values that differ per environment, and all secrets, should come from outside the code.

Q: Can I use production data in staging to test realistically?

Only after removing or anonymising personal information. Real customer data in lower-security environments is a leak waiting to happen.

Q: What is "twelve-factor"?

A well-known checklist for deployable apps. Two big ones: config in the environment and dev/prod as similar as possible.

✏️ Sharpen your pencil: spot the mistakes

A repo contains: app.py, .env (with real keys), .env.example, requirements.txt. Which file shouldn't be committed, and what's missing?
Answer: .env should be listed in .gitignore and not committed. Also a lock file (exact versions) and a README with setup steps would help.

Key points
  • Same code, different configuration per environment (dev, staging, prod).
  • Read config from environment variables; never hard-code or commit secrets.
  • Commit .env.example, ignore .env; rotate any leaked secret immediately.
  • Pin dependencies; keep environments similar; use feature flags for safe rollouts.

Configuration via environment variables

# shell
export DATABASE_URL="postgres://app:***@db.internal:5432/shop"
export DEBUG=false

# code
import os
db_url = os.environ["DATABASE_URL"]            # fail loudly if missing
debug = os.environ.get("DEBUG", "false") == "true"
  • Local dev: a .env file loaded by the tool; add it to .gitignore; commit a .env.example with fake values.
  • Twelve-Factor App principle: strict separation of config from code; store it in the environment; treat logs as streams; stateless processes; dev/prod parity.
  • Validate config at startup, so the app fails immediately rather than at 2 a.m.

Secrets

  • API keys, DB passwords, signing keys, tokens. Never in git, chat, logs, screenshots or client-side code (anything in browser JS is public).
  • Use a secrets manager (AWS Secrets Manager, Vault, cloud platform secrets) and least privilege: each service gets only the access it needs.
  • Rotate regularly and immediately if leaked. Bots scan GitHub for keys within minutes.
  • Different secrets per environment: a dev key must not open production.

Dependencies and reproducibility

  • Declare dependencies (requirements.txt, package.json) and lock exact versions (package-lock.json, poetry.lock).
  • Isolate per project: Python virtualenv, Node's local node_modules, or containers (next module).
  • Feature flags toggle features per environment/user without redeploying.
  • Infrastructure as Code (Terraform) records environment setup in files.
