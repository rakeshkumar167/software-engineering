22. Concurrency and Async: Threads, Event Loops, Race Conditions

Doing many things at once without breaking things.

☕ Start here: the one-person coffee shop

A story Sam runs a coffee shop alone. A customer orders a latte. Sam starts the machine: the milk takes 2 minutes to steam. A bad Sam stands staring at the milk while 10 customers queue up. A smart Sam starts the milk, then takes the next order, serves a croissant, and returns when the machine beeps.

Sam is a single thread, but never idles while waiting. That's async / event-loop concurrency: lots of waiting, one worker, no wasted time.

Now the shop gets busy and hires 3 more baristas (threads / processes). Faster! But now two baristas grab the last carton of milk at the same moment...

Concurrency vs parallelism

  Concurrency: ONE worker juggling many tasks (switching when one waits)
     task A ─▇▇░░░▇▇░░         ▇ working   ░ waiting (network, disk)
     task B ─░░▇▇▇░░▇▇

  Parallelism: MANY workers truly working at the same instant (multiple CPU cores)
     core 1 ─▇▇▇▇▇▇▇▇
     core 2 ─▇▇▇▇▇▇▇▇

Tasks that mostly wait (network, database, disk) are I/O-bound: async or threads help. Tasks that crunch numbers (video encoding) are CPU-bound: you need more cores (multiple processes).

Async/await: do other things while waiting

// Slow: waits for each, one after another  (~2 seconds)
const user  = await fetch("/api/user");      // wait 1s
const posts = await fetch("/api/posts");     // wait 1s

// Fast: start both, THEN wait for both        (~1 second)
const [user, posts] = await Promise.all([
  fetch("/api/user"),
  fetch("/api/posts"),
]);

await means "pause me here, let other tasks run, wake me when it's ready." A Promise (JS) or Future is an IOU for a value arriving later.

Never block the event loop: in a single-threaded server a 5-second CPU loop freezes every user. Offload heavy work to another process or a job queue.

Race conditions: two baristas, one carton of milk

  counter = 5
  Thread A: read 5 ─────────► compute 6 ─► write 6
  Thread B:      read 5 ─► compute 6 ─► write 6          result: 6 ... should be 7!
                 (both read BEFORE either wrote: one update lost)
import threading
count = 0
def work():
    global count
    for _ in range(100_000):
        count += 1                # NOT atomic: read, add, write
threads = [threading.Thread(target=work) for _ in range(4)]
[t.start() for t in threads]; [t.join() for t in threads]
print(count)     # expected 400000. Often LESS. Run it a few times!

# fix: protect the critical section
lock = threading.Lock()
def work_safe():
    global count
    for _ in range(100_000):
        with lock:                # only one thread at a time in here
            count += 1

Deadlock: two polite people at a doorway

Thread AI hold lock 1. I'm waiting for lock 2.

Thread BI hold lock 2. I'm waiting for lock 1.

Both...(waiting forever)...

Avoid by always taking locks in the same order, using timeouts, or better, not sharing mutable data at all.

Ways to dodge the whole mess

  • Share nothing: each worker has its own data; pass messages through a queue.
  • Immutable data: can't be changed, so can't be corrupted.
  • Let the database handle it: one atomic statement beats read-modify-write in your code: 
    UPDATE items SET stock = stock - 1 WHERE id = 7 AND stock > 0;   -- no oversell!
  • Job queues: web request returns immediately ("we'll email you"), a background worker does the slow job.
Brain powerTwo shoppers buy the last concert ticket at the same millisecond. Why might both succeed if your code does "read stock → check → write stock-1"? Both read stock = 1 before either writes. Use a database transaction with locking or an atomic conditional UPDATE.

There are no Dumb Questions

Q: Should I use threads or async?

For lots of waiting on I/O (web servers): async is lightweight and popular. For CPU-heavy work: multiple processes. Threads are the middle option when libraries aren't async.

Q: Why is concurrency bug-hunting so hard?

Bugs depend on timing, so they appear once in a thousand runs and vanish when you add print statements. Prefer simple designs that avoid shared state.

Q: Python's GIL: what is it?

A lock letting only one thread run Python code at a time. Threads still help with I/O waiting, but for CPU-bound work use multiple processes.

✏️ Sharpen your pencil: sequential or concurrent?

You must download 10 files, each takes 1 second. How long if done one after another? With concurrency (assuming enough bandwidth)?
Answer: ~10 s sequentially; ~1 s concurrently (the waits overlap). That's why Promise.all / asyncio.gather matter.

Key points
  • Concurrency = juggling many tasks; parallelism = truly simultaneous work on multiple cores.
  • I/O-bound → async/threads; CPU-bound → multiple processes.
  • Shared mutable data creates race conditions and deadlocks: lock, or avoid sharing.
  • Never block the event loop; push slow work to background jobs.

📋 Quick reference: the details

Key ideaConcurrency = dealing with many tasks in overlapping time. Parallelism = actually executing at the same instant on multiple CPU cores. Concurrency is about structure, parallelism about hardware.

Why bother?

A web server must handle thousands of clients. Most of the time a request is waiting (for the database, network, disk): I/O-bound. Work that burns CPU (image resize, encryption) is CPU-bound. The solution differs.

Models

Async/await

// Sequential: ~2 s
const a = await fetch("/slow-a");   // wait 1 s
const b = await fetch("/slow-b");   // wait 1 s

// Concurrent: ~1 s
const [a, b] = await Promise.all([fetch("/slow-a"), fetch("/slow-b")]);

await means "pause this task, let others run until the result is ready". A Promise/Future represents a value arriving later. Never block the event loop (long loops, sync file reads).

Shared state problems

  • Race condition: result depends on timing. Two threads do counter += 1: both read 5, both write 6. One update lost.
  • Fix: lock/mutex so only one thread enters the critical section; atomic operations; or avoid sharing (immutable data, message passing, queues).
  • Deadlock: A waits for B's lock while B waits for A's. Avoid by acquiring locks in a consistent order, using timeouts.
  • Starvation, and the same problem in databases (two requests updating one row), solved with transactions/locking.
  • Races are timing dependent: tests may pass 999 times and fail once. Prefer simple designs.

Practical advice

  • Use the framework's model (gunicorn workers, Node event loop) before inventing your own.
  • Offload slow work to a job queue (Celery, SQS): respond fast, process later.
  • Use timeouts, limit concurrency (worker pools), and make retries idempotent.
