29. Working with AI Tools

AI assistants are powerful and fast. The responsibility for the result stays with you.

🧑‍🍳 Start here: the brilliant, overconfident intern

A story Imagine an intern who has read every programming book and website ever written. They answer instantly, never get tired, and write plausible code for almost anything.

But sometimes they confidently invent a function that doesn't exist, miss a security hole, or "fix" a failing test by faking its answer. And they don't know your project unless you tell them.

That's an AI coding assistant. Hugely useful, if you treat it as a fast junior colleague whose work you must review, never as an oracle. You are responsible for what ships.

How it works (just enough to use it wisely)

   your prompt + any files you share (the "context")
              │
              ▼
   ┌───────────────────────────────┐
   │  Large Language Model         │   learned patterns from huge amounts of text & code
   │  predicts the most likely     │   it does NOT "look up" facts unless given tools
   │  next words, one at a time    │
   └───────────────────────────────┘
              │
              ▼
   fluent answer: sometimes brilliant, sometimes wrong ("hallucination")
  • It only knows what's in its context (your messages and files) plus its training. Missing info means it guesses.
  • Agents add tools (read files, run tests, search) in a loop, so they can check their own work.
  • Because it predicts what sounds right, a wrong answer sounds exactly as confident as a right one.

Great uses

  • 🔎 Explain unfamiliar code, error messages, or concepts ("explain this stack trace step by step").
  • 🧱 Boilerplate: scaffolding, config files, regexes, shell one-liners, format conversion.
  • 🧪 Draft tests and suggest edge cases you hadn't thought of.
  • 👀 Review your code for bugs, clarity, security.
  • 🎓 Learn: "quiz me on HTTP", "give me an analogy", "what's wrong with my explanation?"

Prompting that works: be a good manager

Weak prompt"make login work"

Strong prompt"Flask 3 + SQLAlchemy app. POST /login should check a bcrypt-hashed password from the users table and set an HttpOnly, Secure session cookie. Current code and the error are below. Don't change the DB schema. Add pytest tests for wrong password and unknown email."

  1. Context: language, versions, goal, what you've tried, the exact error text.
  2. Constraints: "no new dependencies", "keep the existing function names".
  3. Examples: sample input and expected output.
  4. Small steps: one change at a time you can review, rather than "build my whole app".
  5. Iterate: "that fails with this error", "why did you choose X?", "what are the alternatives?"

The verification habit (non-negotiable)

   AI suggests code
        │
        ▼  1. READ it: can you explain every line?
        ▼  2. RUN it + run the tests (add some of your own, incl. edge cases)
        ▼  3. CHECK the docs: do these functions/options exist in YOUR version?
        ▼  4. REVIEW for security: injection? missing auth check? hard-coded secret?
        ▼  5. COMMIT in a small step (git), so a bad change is easy to undo
        ✔ ship
Watch for: invented APIs; outdated practices; code that makes a test pass by hard-coding the expected answer; needless complexity; "fixes" that silence an error instead of solving the cause. Read the diff, not just the green checkmark.
Brain powerAn assistant tells you "use pandas.read_csv(path, fast_parse=True)". You've never seen that option. What do you do? Check the official docs for your pandas version. If fast_parse doesn't exist, it was hallucinated. Never assume a confident answer is a true one.

Privacy, honesty and learning

  • Don't paste secrets (API keys, passwords), customer data or private company code into tools your organisation hasn't approved. Know the data policy.
  • Follow your school's/employer's rules on AI use; cite or disclose where required. Respect licences.
  • Try first, then ask. Struggling for 15 minutes builds understanding. Letting AI do all your thinking means you can't judge its answers.
  • Ask it to teach: "explain why", "quiz me", "critique my solution", and then test what it says by running things yourself.
  • The fundamentals in modules 1 to 28 matter more now: you can only direct and verify what you understand.

A sample healthy workflow

  1. Write down what you want in plain words (and what "done" looks like)
  2. Ask the AI for a plan; read it; fix misunderstandings
  3. Implement in small steps (you or the AI), one commit each
  4. Run the tests after EVERY step; paste failures back
  5. Ask for a review: "what edge cases or security issues did we miss?"
  6. YOU read the final diff and take responsibility

There are no Dumb Questions

Q: Will AI replace programmers?

It changes the work: less typing boilerplate, more specifying, reviewing, designing and verifying. People who understand systems well, as this course teaches, are better placed to use it effectively.

Q: It gave me different answers when I asked twice. Why?

Its output involves randomness, and small prompt differences change results. That's another reason to verify with tests rather than trust any single answer.

Q: Can I use AI for school assignments?

Only as your instructor permits. Even when allowed, make sure you could explain and rebuild the solution yourself; the point of the assignment is your learning.

Improve: "my page is broken fix it".
Answer (example): "My HTML page (Chrome 126) shows a blank screen after clicking Submit. The console shows Uncaught TypeError: Cannot read properties of null (reading 'value') at app.js:14. Here's app.js and the form HTML. What's the likely cause, and how can I confirm it before changing anything?"

Key points
  • AI assistants are fast, fluent and sometimes confidently wrong; treat them as a junior colleague.
  • Give rich context and constraints; work in small, reviewable steps.
  • Always read, run, test, check docs and review security; you own what you ship.
  • Protect secrets and private data; follow usage rules; use AI to learn, not to skip learning.

📋 Quick reference: the details

Key ideaTreat an AI assistant like a very fast, well-read junior colleague who is sometimes confidently wrong. You own what you ship: understand it, test it, review it.

How LLM assistants work (just enough)

  • A large language model predicts likely next text from patterns learned in training. It doesn't "look things up" unless given tools, and it can produce plausible but false output (hallucination), e.g. a function or API that doesn't exist.
  • It sees only its context window: your prompt, pasted files, conversation. Missing context means guessing.
  • Agents add tools (read files, run commands, run tests, browse) in a loop, so they can check their own work.

Where they shine

  • Explaining unfamiliar code, errors, concepts ("explain this stack trace").
  • Boilerplate, scaffolding, tests, regexes, shell one-liners, format conversions.
  • Exploring options, reviewing code for issues, drafting docs, refactoring with tests as a safety net.
  • Learning: ask for analogies, quizzes and step-by-step reasoning (not just the answer).

Prompting that works

  1. Give context: language, framework, versions, goal, what you've tried, the exact error.
  2. Be specific about the outcome and constraints ("no new dependencies", "must handle empty input").
  3. Show examples of input and expected output.
  4. Break big tasks into steps; review each.
  5. Iterate: point out what's wrong. Ask it to explain its choices and alternatives.
  6. Let it run the tests; paste failing output back.
Weak:  "make my login work"
Better: "Flask 3 app. POST /login should verify a bcrypt hash from the users table
        (SQLAlchemy) and set a session cookie (HttpOnly, Secure). Here is my
        current code and the error. Don't change the DB schema. Add pytest tests."

Verify everything

  • Read the code. If you can't explain a line, don't ship it.
  • Run and test it, including edge cases. Check that APIs/libraries exist and match your version (read the docs).
  • Review for security (modules 14, 17, 28): SQL injection, missing authorization, hard-coded secrets, outdated practices.
  • Prefer small changes you can review and commit with git (module 7) so bad suggestions are easy to revert.
  • Watch for over-engineering and for code that makes tests pass by special-casing them.

Privacy, ethics, and learning

  • Don't paste secrets, customer data or confidential code into tools your organisation hasn't approved. Know the data policy.
  • Respect licences and your school/employer's rules on AI use; disclose where required. Submitting AI work as your own understanding defeats learning.
  • Use AI to learn faster: try first, then compare; ask it to quiz you. Skills (debugging, design, reading code) are what let you judge its output.
  • Fundamentals from modules 1-28 matter more, not less: you can only direct and check what you understand.
