26. Logging, Monitoring, Observability and Incident Basics

You can't fix what you can't see, and production is where you can't attach a debugger.

🏥 Start here: the hospital monitor

A story A patient in intensive care is wired to machines: a heart-rate graph, blood pressure, oxygen level, and a chart where nurses write down everything that happens. Nobody stares at the patient hoping to guess they're okay.

Your live software needs the same. Once it's running on a server, you can't attach a debugger or watch it with your own eyes. You need it to report how it's doing:
📝 Logs = the nurse's chart (what happened, when)
📈 Metrics = the vital-signs graphs (numbers over time)
🧭 Traces = a tracking number following one request through every department
🚨 Alerts = the alarm that wakes a doctor

Logs: write down what's happening

import logging, json
log = logging.getLogger("checkout")

log.info("order placed", extra={"order_id": 991, "user_id": 42, "total": 30.0})
log.error("payment failed", extra={"order_id": 991, "reason": "card_declined"})

# what ends up on the server (structured JSON, searchable!)
{"ts":"2026-11-20T10:03:11Z","level":"ERROR","service":"checkout",
 "request_id":"7f3a9c","msg":"payment failed","order_id":991,"reason":"card_declined"}
LevelUse
DEBUGFine detail for developers (off in production)
INFONormal milestones ("order placed")
WARNINGOdd but survivable ("retrying payment")
ERRORSomething failed
CRITICALSystem is going down
Never log passwords, tokens, full card numbers or sensitive personal data. Logs are copied, searched and kept for a long time by many people.

Request ID trick: give every incoming request a unique ID and include it in every log line. When a customer says "my order failed", you search that one ID and see the entire story across all services.

Metrics: the vital signs

Numbers sampled over time, shown as graphs. The four golden signals to watch for any service:

  🕐 LATENCY     how long do requests take?
  📊 TRAFFIC     how many requests per second?
  ❌ ERRORS      what % of requests fail?
  🔥 SATURATION  how "full" is the system? (CPU, memory, disk, connections)
Brain powerAverage response time is 100 ms, but users complain it's slow. How can both be true? Averages hide the tail. If 5% of users wait 3 seconds, the average still looks fine. Look at percentiles: p50, p95, p99.

Traces: follow one request through the maze

  request 7f3a9c   total 850 ms
  ├─ web server            ███ 40 ms
  ├─ auth service          ██ 30 ms
  ├─ order service         ██████████████████ 700 ms   ◄── the slow part!
  │   └─ database query    ████████████████ 650 ms     ◄── specifically THIS
  └─ send response         █ 20 ms

Tools: Prometheus + Grafana (metrics), Loki/ELK/CloudWatch (logs), OpenTelemetry + Jaeger (traces), Datadog (all-in-one), Sentry (error tracking).

Alerts: wake me only when it matters

  • Alert on what users feel (error rate, latency), not every CPU blip.
  • Every alert must be actionable. Constant false alarms cause alert fatigue and people ignore the real one.
  • Health endpoint (/healthz returns 200) lets load balancers and monitors check the app is alive.
  • SLO (Service Level Objective): "99.9% of requests succeed in under 500 ms." The allowed failure is your error budget.

When it breaks: incident basics

  DETECT ► TRIAGE ► MITIGATE FIRST ► COMMUNICATE ► ROOT CAUSE ► POSTMORTEM
  (alert)  (how bad?   (rollback, turn   (status page,   (why, really?)  (what will we
           who's on     off feature,      tell users)                     change? no blame)
           call?)       scale up)

The first goal is stop the pain (roll back!), not find the culprit. After it's over, write a blameless postmortem: timeline, causes, and improvements to the system. People make mistakes; good systems make them hard to do.

There are no Dumb Questions

Q: Monitoring vs observability?

Monitoring asks questions you thought of in advance ("is CPU high?"). Observability gives you rich enough data to investigate questions you didn't anticipate.

Q: Where do logs go in a container?

Write them to stdout; the platform collects them. Don't write log files inside a container that disappears.

Q: Can I log too much?

Yes: costs money and buries the signal. Log events with useful context, not every line of execution.

✏️ Sharpen your pencil: which signal?

(1) "Which of my 6 microservices made checkout slow?" (2) "How many 500 errors per minute?" (3) "Why did order 991 fail?"
Answer: (1) trace, (2) metric, (3) logs (searched by order or request ID).

Key points
  • Observability = logs (events), metrics (numbers), traces (request journeys).
  • Use structured logs with request IDs; never log secrets.
  • Watch latency, traffic, errors, saturation; use percentiles, not averages.
  • Alerts must be actionable; in an incident, mitigate first, then investigate, then learn blamelessly.

📋 Quick reference: the details

Key ideaMonitoring tells you that something is wrong (known questions). Observability lets you work out why (new questions) from the data your system emits: logs, metrics, traces.

Logging well

{"ts":"2026-11-20T10:03:11Z","level":"ERROR","service":"checkout",
 "request_id":"7f3a9c","user_id":42,"msg":"payment failed","error":"card_declined","ms":812}
  • Levels: DEBUG, INFO, WARNING, ERROR, CRITICAL. Production usually INFO+.
  • Structured (JSON) logs are searchable. Include a request/correlation ID to follow one request across services.
  • Log to stdout; the platform collects it (ELK, Loki, CloudWatch, Datadog).
  • Never log passwords, tokens, full card numbers or sensitive personal data.
  • Log what happened and context, not noise. Too much hides the signal and costs money.

Metrics that matter

  • Golden signals: latency, traffic, errors, saturation (how full the resource is).
  • Use percentiles (p50, p95, p99), not averages: average 100 ms can hide 5% of users waiting 5 s.
  • SLI / SLO / SLA: indicator (measured, e.g. % successful requests), objective (target, 99.9%), agreement (contract with penalties). An error budget is the allowed failure.
  • Tools: Prometheus + Grafana, Datadog, CloudWatch. Tracing: OpenTelemetry, Jaeger.
  • Health endpoints (/healthz) used by load balancers (module 16) and orchestrators.

Alerting and incidents

  • Alert on symptoms users feel (error rate, latency), not every CPU blip. Each alert should be actionable; alert fatigue is dangerous.
  • Incident flow: detect → triage (severity, who's on call) → mitigate first (rollback, disable feature, scale) → communicate → find root cause → restore.
  • Blameless postmortem: timeline, root causes, what went well, action items. Focus on systems, not people.
  • Also monitor from outside (synthetic checks) and watch certificate/domain expiry.
