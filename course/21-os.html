21. Operating System Concepts: Memory, Filesystems, Sockets

The layer between your code and the hardware. Module 1 revisited.

🏛️ Start here: the building manager

A story Picture an apartment building. Dozens of tenants (processes) live inside. They don't connect their own plumbing or wiring: the building manager (the operating system kernel) does:
🛋️ assigns each tenant their own private flat (memory),
🗄️ runs the shared storage room (file system),
📬 handles the mailroom (network),
⏱️ schedules who uses the shared lift and when (CPU time).

Tenants must ask politely via the front desk (system calls): "please open this file," "please send this data." They can't just walk into the machine room.

Try: strace ls on Linux (or dtruss ls on macOS, as admin) to watch a simple command make dozens of system calls.

Memory: private flats and the overflow storage

  • RAM: fast, small, forgets on power-off. Disk: slower, big, remembers.
  • Virtual memory: every process believes it has the whole memory to itself. The OS secretly maps its addresses to real RAM, so processes can't peek at each other (isolation, module 1).
  • Swap: when RAM fills, the OS parks rarely-used chunks on disk. Works, but everything slows to a crawl ("thrashing").
  Process's view                       Reality
  ┌─────────────┐ ← "my memory"         RAM: [A][B][A][C][B][free]
  │ stack ↓     │                       disk (swap): [A-old-stuff]
  │   ...       │
  │ heap  ↑     │
  │ code        │
  • Stack: function calls and local variables; neat, automatic, small. Infinite recursion → "stack overflow".
  • Heap: for data that outlives a function; bigger, managed. Forget to free it → memory leak (the process grows until the OS kills it).

File systems: everything is a file

  • A tree of directories and files; the OS turns names into locations on disk.
  • Opening anything (file, pipe, network connection) hands you a small integer, a file descriptor. There's a limit per process: "too many open files" means you forgot to close some.
  • Disks fill up, and a full disk crashes servers in funny ways (logs, temp files). Monitor it!

Your web server, revealed as system calls

  socket()   ← "give me a network endpoint"
  bind(8000) ← "attach it to port 8000"           (error: "address already in use" = taken!)
  listen()   ← "start waiting for visitors"
  ┌ accept() ← "a visitor connected; here's a new connection"
  │ read()   ← get the HTTP request bytes
  │ write()  ← send the HTTP response bytes
  └ close()  ← hang up, loop back to accept()

Find who's using a port: lsof -i :8000.

There are no Dumb Questions

Q: Is Linux "the OS" or "the kernel"?

Technically Linux is the kernel; "distributions" (Ubuntu, Debian…) bundle it with tools. Most servers and Android run it; macOS and Windows have their own kernels.

Q: What's a daemon / service?

A process meant to run in the background for a long time (web server, database), started and restarted by systemd/launchd.

Q: What's the OOM killer?

When the system truly runs out of memory, the kernel picks a hungry process and kills it to save the rest.

✏️ Sharpen your pencil: match the symptom

(1) "Address already in use". (2) Server freezes, disk light blinking nonstop, RAM full. (3) "Too many open files". (4) Process memory climbs forever.
Answer: (1) another process owns the port; (2) swapping/thrashing; (3) file descriptors leaked or limit too low; (4) memory leak.

Key points
  • The kernel manages CPU, memory, files and network; programs use system calls.
  • Virtual memory isolates processes; swap saves you but is slow; leaks kill long-running programs.
  • RAM is ~1000× faster than SSD and ~1,000,000× faster than a trans-ocean network call.
  • Everything is a file descriptor; sockets power servers; signals control processes.

📋 Quick reference: the details

Key ideaThe OS kernel manages shared hardware (CPU, memory, disk, network) and offers programs a safe, simple interface through system calls. Programs never touch hardware directly.

Kernel space, user space, system calls

  • User space: your program, restricted. Kernel space: privileged OS code.
  • To open a file, send network data, or start a process, your program makes a system call (open, read, write, socket, fork). Language libraries wrap these.
  • Peek: strace ls (Linux) or dtruss (macOS) shows them.

Memory

  • RAM is fast, temporary, limited. Disk is slow, persistent. (Rough latency: CPU cache ns, RAM ~100 ns, SSD ~100 µs, network across continents ~100 ms.)
  • Virtual memory: each process sees its own private address space; the OS maps it to real RAM in pages. This is how isolation works.
  • Swap: when RAM is full the OS moves pages to disk, making everything very slow ("thrashing").
  • Stack (function calls, local variables; overflow with endless recursion) vs heap (dynamic allocation).
  • Memory leak: memory kept but never freed → process grows until the OS kills it (OOM killer). Languages with garbage collection free unreachable objects automatically; C/C++ need manual care.

Filesystems

  • Organises bytes into files and directories (tree). Types: ext4, NTFS, APFS.
  • Everything is a file descriptor (an integer handle): files, pipes, and network sockets (Unix: "everything is a file").
  • Limits: open file descriptors per process ("too many open files"), disk space, inodes.
  • Permissions and ownership (module 6). Writes are buffered; fsync forces them to disk.
  • Symlinks point to other paths. Temp files, logs and disks can fill up and crash servers.

Sockets and the network

Your HTTP server (module 4) does roughly: socket() → bind(port) → listen() → loop accept() → read() request → write() response → close(). "Address already in use" means another process holds that port (lsof -i :8000).

Processes and signals

  • fork/exec: how a shell starts programs. Signals notify processes: SIGINT (Ctrl+C), SIGTERM (polite stop, allows cleanup), SIGKILL (immediate, can't be caught).
  • Daemons/services run in the background; managed by systemd/launchd. A zombie is a finished child its parent hasn't collected.
  • Scheduling: context switch swaps which process runs; cost adds up with too many threads.
