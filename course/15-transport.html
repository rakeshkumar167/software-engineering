15. TCP vs UDP, TLS in Detail, WebSockets, HTTP/2 and HTTP/3

Going one layer deeper into how bytes actually travel.

📞 Start here: letters vs phone calls vs walkie-talkies

A story Three ways to talk:
📦 Registered mail (TCP): every letter is numbered and signed for. Lost one? It's re-sent. Arrives in order. Slower, but reliable.
📮 Throwing postcards in a mailbox (UDP): no tracking, no resend. Fast and cheap. A few may be lost.
📻 An open phone line (WebSocket): both sides can talk any time, no re-dialling.

Choosing the right one is the whole story of this chapter.

TCP: the careful courier

Before sending anything, TCP does a three-way handshake, a polite "hello":

  Client                    Server
    │ ── SYN  ("can we talk?") ──►│
    │ ◄─ SYN-ACK ("yes, can you hear me?") ─│
    │ ── ACK  ("loud and clear") ─►│
    │ ═══════ data flows ═════════ │  every chunk numbered; missing ones re-sent
  • Guarantees order and delivery. Used for web pages, email, file transfer, databases.
  • Cost: the handshake, plus waiting for lost pieces (a delay called head-of-line blocking).

UDP: the "just send it" postcard

No handshake, no numbering, no resending. Use it when late is worse than lost:

  • Video call: if a frame from 2 seconds ago arrives now, it's worthless. Skip it.
  • Online games: your position now matters, not 3 updates ago.
  • DNS: tiny question, tiny answer. If it fails, just ask again.

TLS handshake, in plain words

BrowserHi example.com! I speak TLS 1.3 and these ciphers.

ServerLet's use this one. Here's my certificate, my ID card, signed by a Certificate Authority.

BrowserChecking... name matches ✔, not expired ✔, signed by someone I trust ✔. Here's my half of a secret.

ServerAnd here's mine. We can both now compute the same key without anyone listening in being able to.

Both🔒 Everything from here on is encrypted.

The clever bit is that both sides end up with the same secret key without ever sending it. The key is thrown away afterwards (forward secrecy), so even if the server's private key is stolen next year, today's conversation stays unreadable.

HTTP, three generations

  HTTP/1.1   one request at a time per connection  (browsers open ~6 connections)
              [req1]───[resp1]  [req2]───[resp2]  ...  (a slow one blocks the line)

  HTTP/2     MANY requests share ONE connection (multiplexing)
              [req1][req2][req3] interleaved   …but one lost TCP packet stalls ALL

  HTTP/3     same idea over QUIC (built on UDP):
              loss on one stream doesn't block others; faster setup; survives Wi-Fi → 4G switch

Good news: your code (GET, 200 OK, headers) looks the same in all three. The upgrade happens underneath.

There are no Dumb Questions

Q: What exactly is a "socket"?

The OS's "phone jack" for network talk: an endpoint identified by IP + port + protocol that your program reads from and writes to.

Q: Does HTTPS slow things down?

A tiny bit at connection start; modern TLS and HTTP/2/3 made it negligible. The security is worth it.

Q: How can a certificate expire and break a site?

Certificates have an end date. When it passes, browsers refuse the connection with a scary warning. Automate renewal (Let's Encrypt does this).

✏️ Sharpen your pencil: TCP or UDP?

(1) Downloading a PDF. (2) A live voice call. (3) Sending an email. (4) A fast multiplayer shooter's position updates.
Answer: (1) TCP, (2) UDP, (3) TCP, (4) UDP.

Key points
  • TCP = reliable and ordered (handshake, retransmit). UDP = fast and best-effort.
  • TLS verifies the server's certificate and creates a shared secret key; traffic is then encrypted.
  • HTTP/2 multiplexes requests; HTTP/3 runs on QUIC/UDP for smoother, faster connections.
  • Real-time: polling, SSE (one-way), WebSocket (two-way).

A socket is the OS endpoint (IP + port + protocol) a process uses to send/receive. Your server from module 4 listens on a TCP socket.

TLS handshake in more detail

  1. ClientHello: supported TLS versions, cipher suites, random number, the hostname (SNI).
  2. ServerHello + certificate chain: server picks the cipher and presents its cert.
  3. Client validates chain to a trusted root CA, checks hostname and dates.
  4. Both sides derive a shared session key using key exchange (ephemeral Diffie-Hellman, which gives forward secrecy: stealing the server key later doesn't decrypt past traffic).
  5. Encrypted application data flows using fast symmetric encryption (e.g. AES-GCM).

TLS 1.3 needs 1 round trip (0-RTT on resumption). Certificates are issued free by CAs like Let's Encrypt and renewed automatically.

HTTP versions

VersionKey improvement
HTTP/1.1Text; keep-alive connections; one request at a time per connection (head-of-line blocking), so browsers open several connections
HTTP/2Binary framing, multiplexing many requests on one TCP connection, header compression. A lost TCP packet still stalls all streams.
HTTP/3Runs over QUIC (on UDP): per-stream loss recovery, TLS 1.3 built in, faster connection setup, survives network switch (Wi-Fi → mobile)

HTTP semantics (methods, status codes, headers) stay the same across versions.

WebSockets and other real-time options

  • HTTP is request→response; the server can't speak first. WebSocket upgrades one HTTP connection (Upgrade: websocket, status 101) into a persistent two-way channel. Good for chat, live dashboards, multiplayer.
  • Server-Sent Events (SSE): one-way server → client stream over plain HTTP; simpler for notifications.
  • Long polling: client asks, server holds the request open until there's news.
  • Trade-off: persistent connections use server resources and complicate scaling.
